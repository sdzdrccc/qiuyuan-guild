### 4. ❌ CSV 一个未转义逗号，生成物被静默截断

`data/datas/qydl_game_config.csv` **第 10 行**（`spirit_root_variant_value` 的 `comment` 列）含一个 ASCII 逗号：

## 四、门禁落地（本次已实现 · B 档）

> 按大人选择：**只落「可机械执行」的部分（门禁）＋ 出提案**，**不改真源文档、不落 ADR**。

| 脚本 | 规则 | 治的是 §二的哪一条 |
|---|---|---|
| `scripts/check-data.js` | **新增 `R10`** 配置表**内容**断言（4 条子规则：CSV 字段数 = `##var` 列数 · `prob_ppm` 合计 = 1000000 · 倍率两列单调 · 公式① 手算复现） | 缺陷 3 · 4 |
| `scripts/check-contract-gate.js` | **新增 `G1`**：`ROADMAP` 声明「新增展开」的实体，`contracts/` 里**必须真有展开节** | 缺陷 1b |
| `scripts/check-identifiers.js` | **新增 `I1`**：文档引用的配置表 / 数据库表标识符**必须存在**；退役名须**同行标明退役** | 缺陷 4（引用面）· 5 |
| `scripts/check-records.js` | **新增 `C1`~`C5`**：记录必备节 · 台账↔正文双向核对 · 审核结论二值 · 契约变更须 L3 终审 · **改了实现就必须有同批记录** | 缺陷 2 · 3（判据面）|

**三条设计纪律（本轮实测踩出来的）**：

1. **误报率高的门禁 = 没有门禁。** `check-identifiers.js` 首版用「键名前缀」等宽判据，实测 **44 个误报**
   （误报 MySQL 表名、原型占位名 `xx_*`、示例占位符 `qydl_xxx`、以及**历史记录里本该保留的旧名**）。
   → 收紧为**三个高信号命名空间**（`qydl_*` / `*_ppm` / `*_config`），并**排除 `records/`**（历史留痕按纪律「只追加不改写」本就该保留旧名）。
   → 最终 **1 错 + 2 警告，全部为真**。**漏报多于误报，是这个取舍的自觉代价。**
2. **脚本假装能判语义 = 虚假的安心。** `check-records.js` 的 `C3`（禁评分）首版扫全文，误报了 `X-0002`
   —— 那篇记录正在**引用 `ADR-0008` 规则本身**（「新增 ADR-0008（禁主观评分）」）。
   → 改为**只看「审核」节** + 行内出现「禁 / 不得 / 评分制 / ADR-0008」时**豁免该行**（是在讲规则，不是在评分）。
3. **存量与新增必须分开算。** `C3`/`C4`/`C5` 揭示的是**历史存量缺口**（7 篇记录无审核节、dalu 5 笔提交无记录）。
   把存量一律判红 = 门禁一上线就**永久红** = 被无视（§7.1 纪律 4「不许给未来埋雷」）。
   → 以 **`GATE_EPOCH`**（本脚本诞生时两仓 HEAD）为界：**之前 → `warn` 并逐条列出**；**之后 → `err`**。
   → **既不是虚假的安心**（存量全部点名列于 §六），**也不会变成永远误报**。

## 五、流程完善提案（**未改真源 · 待大人裁定**）

> 核心判断：**本轮查到的失败，几乎都不是「方案缺规则」** ——
> 方案 §4（契约先行）/ §5（消费者审核 + 分级）/ §6（强制记录 + 台账查账）**都已写得很清楚**。
> 失败在于**规则没有执行载体**。这正是方案 §11.6 与 `CONVENTIONS.md` §7.2 自己点名的病：
> 「**同一个规则在文档里写了三遍还不被执行，它就该做成门禁，而不是再写第四遍**」。
> **故本提案以「补载体」为主，以「补规则」为辅。**

### ③ 与 ⑦ 的详细说明（两条新机制 · 需要大人点头）

**③ 「待实现规则」登记位** —— 治的是「承诺落在两不管地带」

现状：`SPIRIT-ROOT-FORMULA.md`（dalu 的文件）写「`check-data` 须加 3 条校验」，而 `check-data.js`（guild 的文件）没加，
**没有任何地方记录「这句承诺还没兑现」**。
→ 补法：在脚本里加一个**显式常量**：

```js
// 本脚本承诺但尚未实现的规则 —— 启动了就必须让人看见
const PENDING_RULES = [
  // { id:'R12', from:'X-00xx', desc:'...' },
];
```

启动时若非空 → **打印警告**；`--strict` → **报错**。
→ 好处：**「写了却未加」不再静默**，且这条承诺有了**可查的落点**（不必依赖人的记忆）。

**⑦ 给 guild 侧定义「消费者」** —— 治的是「agent 审 agent 会互相放水」里那个缺口

方案 §5.2 把「审核者 = 下游消费者」讲得很透，但它的表里**没有任何一行覆盖「guild 自己的契约/门禁产物由谁审」**：

|---|---|
| `world` 的配置表 | `combat` + `ui` |
| `combat` 的接口 | `ui` |
| …… | …… |
| **`contracts/` 的契约** | ⚠️ **缺** —— 方案里没定义 |

**今天的事实**：guild 的契约与门禁**落后下游一整天**，**没有人发现**。
→ 补法：`contracts/` 的消费者**就是 dalu**（下游执行方）——
**「下游读不通」= 契约缺东西**，这正是**铁律二**的判据。
→ 落地：dalu 的每张 `T-*` 卡增一节 **「契约回执」**：

```markdown
## 契约回执（下游 → 上游）
- 本次消费：`data-contract.md` §3.1 / §3.2 / §4.1
- 读不通 / 缺定义 / 需变更：
  - `Account` 实体**无字段定义**，但本卡要建 `qydl_account` → 已在 `X-0015` 登记
```

→ **这一条把「契约落后」从「靠人发现」变成「下游每张卡自动上报」**。
→ 本次若早有此机制，§二-1b 那 2 个未展开实体与 6 处偏离，**会在第一张 dalu 卡上就被顶出来**，而不是等审阅。
