# CONVENTIONS.md —— 虬渊大陆工程约定

> **效力**：本文件是**铁律级**约定，与 `docs/AGENTS.md` 同级，**优先级高于任何临时指令**。
>
> **三份文档的分工**：
> | 文件 | 管什么 |
> |---|---|
> | `docs/AGENTS.md` | **AI 的工作纪律**（该读什么、不许做什么） |
> | **本文件** | **工程约定**（契约、数据、命名、记录**长什么样**） |
> | `docs/DECISIONS.md` | **为什么这么定**（ADR 台账，**唯一真源**） |
>
> **升版规则**：本文件的每条约定若要**推翻或放宽**，必须**先开一条 ADR**（`docs/DECISIONS.md`），不许直接改。
>
> **版本**：**v0.4**（2026-09-28）—— 新增 **§9 环境与版本锁定**；**§6.1** 补录资产命名两条线（引擎内 Epic 前缀 / 引擎外上游 kebab）。
> 来源：多 Agent 协作开发方案 §4 / §6 / §8 —— 本文件是它的**固化落地**，方案负责「为什么」，本文件负责「怎么做」。

## 1. 契约先行（顺序不可颠倒）

```
改契约（先落 ADR，arch 裁决）
   → 改实现（模块 owner）
   → 改测试（qa）
   → 记录（强制产出）
```

**反模式**：先写代码或先填表，回头「补一下契约」。
补出来的契约会**退化成文档**，失去约束力 —— 这是整套机制最容易被破的一环。

### 1.1 四条契约铁律

1. **契约是唯一真源** —— 代码与数据**服从**契约，不是反过来。
2. **ADR 只追加** —— 推翻旧裁决 = **新增**一条带 `supersedes: ADR-xxxx` 的 ADR，**历史条目一个字都不许改**。
3. **枚举必须留 `unknown`** —— 凡要向后回填的枚举，必须允许「未核实」取值。否则回填时只能二选一，**标哪个都是撒谎**。
4. **有分歧先查上游** —— `本仓 DECISIONS.md` → `gbe-assets/docs/DECISIONS.md` → `虬渊大陆` 对应页 → 都没有才问大人，答复后**落一条 ADR 再动手**。
5. **契约不含物理映射**（v0.2 新增） —— 表名 / 前缀 / 主键命名 / 存储引擎 / 分片键**归下游**，契约一字不写。详见 §1.2。

### 1.2 契约定义「逻辑模型」，不定义「物理映射」与「文件格式」

> **v0.2 扩写**（2026-09-28）：原为「不定义文件格式」，现**增收物理映射**。依据 `DECISIONS.md` ADR-0001。

**契约管逻辑，物理归下游。** 三者是三件事，别混：

| | 是什么 | 在哪 | 例子 |
|---|---|---|---|
| **逻辑模型** | 实体、字段语义、类型、约束、枚举、公式 | ✅ **契约**（`contracts/`） | 「角色有 `realm_id`，取值 1–9」 |
| **文件格式** | 同一份逻辑的**编码** | 各自工具 | 原型 JSON ／ 正式 Luban 表 |
| **物理映射** | 同一份逻辑的**存储** | ❌ **`qiuyuan-dalu` 自决** | 表名 / 前缀 / 主键名 / 引擎 / 分片键 / 索引 |

**四条判据**：

- **文件格式**：原型 JSON 与 Luban 表应能**无损互转**（写个转换脚本即可验证）。**转不了，说明契约漏了字段。**
- **物理映射**：把契约交给一个**完全不知道表名**的人，他应能设计出**任意一套**表结构并实现它。
- **换库不谈契约**：MySQL → PostgreSQL、改前缀、改分片键 —— 契约**一字不动**。
  **反之**：若某次「换库」逼得契约要改，说明**物理细节漏进了契约**，是违规信号。
- **契约里不出现表名**。陈述「实体 `角色`」，不陈述「表 `xx_characters`」。

> **原型 `xx_` 前缀的地位（v0.2 降级）**：它是**原型作者的占位约定**，**不是需求、不是规范**。
> 需求层（`10-MMO化/技术架构与技术选型.md` §3.4）的表名是 `account` / `role` / `role_attribute` / …（**无前缀**），主键 `role_id`。
> 两套都不是契约内容 —— **正式工程的表名由 `qiuyuan-dalu` 定**，定了也不必回写契约。

## 2. 契约层的三处 schema（层次边界 · 硬性）

生态里现存**两处** schema，加上本仓 `contracts/` —— **是三层，不是三个真源**。

| 层 | 位置 | 管什么 | 变更节奏 |
|---|---|---|---|
| **L1 管线内部** | `gbe-studio/core/contracts/` | 生成管线内部结构（6 个 schema） | 随流水线版本走 |
| **L2 资产包交付** | `gbe-assets/packages/schema/` | 资产**交付包**契约（assembly / validate / index） | 随资产包格式走，**改需 ADR** |
| **L3 游戏侧** | `qiuyuan-guild/contracts/`（**本仓**） | **游戏消费面**：数据模型 / 资产引用 / 协议 / 资源清单 | 随游戏需求走，**改需 ADR** |

**三条层次规则**：

1. **不跨层引用。** L3 **不直接引用 L1** 的 schema —— L3 只认 L2（资产包交付面）。**L1 怎么变是 gbe-studio 的家事，不外溢。**
2. **同层内唯一真源。** 任一层内 schema 只有一份，其余全是消费。
3. **跨层变更必须显式。** 某层改动若影响下层（例：L2 字段改名 → 影响 L3 资产引用契约），**须开跨库台账条目 + 在 `registry/schema-layers.md` 登记**。

> `registry/schema-layers.md` 是这三层的**索引**（每层一行：位置 / 版本 / 负责方 / 最近变更），**不是 schema 副本**。
> 它存在的唯一目的：让「层」这件事**在物理上可见**。

## 3. 数据规范

> **来源（v0.2 修正）**：**需求层 `10-MMO化`（尤其 `技术架构与技术选型.md` §3.4）为主**；原型 `docs/05-dev-conventions.md` 为**参考实作**。
> 首版写「来源：原型（已验证，直接继承）」—— **方向反了**：已验证 = 跑得通，**不等于** = 需求如此。依据 `DECISIONS.md` ADR-0002。

### 3.1 命名：逻辑名 vs 物理名（v0.2 重写）

**分两层，各管各的**：

| 层 | 命名形态 | 谁定 |
|---|---|---|
| **逻辑名**（契约层） | 实体：**单数 PascalCase**（`Role` / `RoleRoot`）<br>字段：**snake_case**、语义清晰、**不缩写**（`realm_id` / `spiritual_root_quality`） | guild |
| **物理名**（存储层） | 表名 / 前后缀 / 主键命名 —— **自由** | `qiuyuan-dalu` |

**对物理层的唯一硬要求**（三条）：

1. **玩家实体的表以 `role_id` 为一级键**，须**可哈希分片**（来源：需求层 `技术架构与技术选型.md` §3.4）。**现在不做分片，但别设计成无法分片的样子。**
2. **每张表必须有表注释，每个字段必须有字段注释**（含义 + 取值范围 / 枚举）。
3. **表名一旦定下，全库一次性统一** —— 不许一半 `xx_` 一半不带。

> **历史留痕**：原型用 `xx_` 前缀（`xx_characters`），需求层用无前缀（`role`）。
> **两者都不是契约内容。** 首版把 `xx_` 写成硬规范，是**让验证用的消耗品去约束交付工程** —— 已在 ADR-0001 废止。

### 3.2 注释（强制）

**逻辑层**：每个实体必须有说明，每个字段必须有字段说明（含义 + 取值范围 / 枚举）。
- 枚举注明取值，如 `境界ID(1=炼气,2=筑基,…)`
- 数值注明范围，如 `灵根纯度(0~100)`

**物理层**（落到建表时）：上述说明**必须转成**真正的 `COMMENT`。
- 迁移 SQL 必须带 `COMMENT`（表 + 字段）。

> ⚠️ 需求层 `技术架构与技术选型.md` §3.4 **只列了玩家表，漏了 `realm_level_config` 等配置表** —— 已登记为待提上游订正项（`data-contract.md` §10.3）。

### 3.3 迁移 SQL 的执行坑

- **含中文的 SQL 必须写成 UTF-8（无 BOM）文件**，再用重定向执行 —— PowerShell 管道直接给 `mysql.exe` 传中文**会乱码**（GBK 字节问题）。
- 查询同样要 `--default-character-set=utf8mb4`，**避免乱码误判**。
- ORM 的 `ddl-auto: update` **只给「新增列」按注释生成注释，不会更新已有列/表的注释** —— 改字段含义时须**手动 ALTER**。

### 3.4 属性不落库

**属性面板由「来源字段」实时派生，不落库**（来源：境界+层次、体质层级、资质品级、每根纯度、主灵根、三负面）。

- 服务端权威计算，客户端与 GM 后台**共用同一份计算结果**。
- 理由：属性是「计算视图」，落库会与来源字段不一致，且公式一调就要全表重刷。

**⚠️ 与需求层的已知差异（v0.2 登记 · v0.3 已裁定）**：
- **必须落库的是「当前值」** —— `hp` / `mp` / `shield` / 寿元现值，这是**状态**。
- **不落库的是「上限值」** —— `hp_max` / 物攻 / 法攻 …，这是**派生**。
- 需求层 `境界基础属性.md` §10.2 的 `role_attribute` 写「落十五项基础属性」——**指的是上限值**，与本条冲突。
- ✅ **已裁定（ADR-0005，「契约胜」）**：**维持现状**（当前值落、上限派生）。
  **处置**：向需求层提**订正单**（走 `qiuyuan-vault-iterate`，在**彼仓**改），**不代写上游**（铁律一）。已登记 `registry/cross-repo-ledger.md`。

> **本条判据**：**属性上限是「计算视图」，不是「状态」。** 落库会与来源字段不一致，且公式一调就要全表重刷。
> **区分口诀**：**会自己变的（生命/灵力现值）落库；能算出来的（上限/攻防）不落。**

## 4. 迁移预留纪律（§8 · 此刻就约束投入）

「先 Godot 原型、后转 UE5」不是口号，它**决定原型期该往哪投钱**。

### 4.0 原型只做验证（第零条）

**原型的每一行代码都是消耗品，原型唯一的产出是「已验证的结论」。**

| 该做 | 不该做 |
|---|---|
| 验证玩法闭环是否成立 | 优化原型性能 |
| 校准数值手感与节奏 | 打磨渲染 / 材质 / 特效 |
| 产出配置表、协议、数值表 | 在原型里堆新功能 |
| 把结论提炼进契约层 | 让 UE5 侧直读原型文件 |

> **判据**：一个改动如果「迁到 UE5 时会被丢掉」，就**不该做**。

### 4.1 数据与逻辑彻底分离

**所有数值进配置表，代码里不出现任何硬编码数值。**

```bash
# 反例检测：脚本里不该有裸数值常量
grep -rnE "=\s*[0-9]+\s*;" --include=*.cs --include=*.go --include=*.cpp . | grep -v "// data-ref"
```

**为什么**：迁移时数据层**零成本保留**，逻辑层**必然重写**。两者缠在一起，迁移成本翻倍。

### 4.2 资产保留无损源 + 中间格式

- 交付基准永远是 **`+Y up / -Z forward / 米`**，**up 轴转换由引擎导入器负责**。
- **消费时不落引擎特有格式**（原型期不生成 Only-Godot 的材质 / 资源文件）。
- **保留原始高精度贴图**（BC 与 ASTC 压缩格式不同，转移动端要重新生成整套）。

### 4.3 场景结构按数据描述，不按引擎节点

布局数据（哪里放什么、坐标、朝向）写进 `resource-manifest.yaml`；引擎的 `.tscn` / `.umap` 只是它的**渲染产物**。

> **判据**：删掉所有场景文件能从 manifest 重新生成 → 合格。做不到，说明布局知识被埋进引擎文件了。

### 4.4 战斗只做「能验证玩法」的最简版

GAS 会全面替换，故：
- ✅ 要做：伤害公式、属性生克、冷却、命中判定的**可验证实现**
- ❌ 不做：性能优化、网络预测、复杂的打断优先级

> 原型的价值在**其数值与公式**，不在其 C# 实现。**提炼公式，丢弃代码。**

### 4.5 服务端：重写 Go（已定）

- **复用** —— `MessageTypes` 协议定义、表结构、迁移 SQL、数值公式
- **丢弃** —— Spring Boot 装配、JPA 实体、22 个服务实现；**Go 侧重新实现，不逐行翻译**
- **判据**：Java 侧某个改动若对「协议或数据表的正确性」无贡献，就**不该做** —— 它迁不到 Go 侧。

### 4.6 迁移承重表（投钱依据）

| 迁移时**零成本保留** → **重投** | 迁移时**必丢** → **浅投** |
|---|---|
| **数据层**（配置表、数值） | 战斗逻辑（GAS 全面替换） |
| **契约层**（数据 / 资产 / 协议） | 场景结构（`.tscn` → `.umap`） |
| **资产无损源文件** | 渲染 / 材质 |

> **一句话**：**原型期把钱花在数据和契约上，别花在引擎特性上。**

## 5. 记录机制

### 5.1 每个任务必须产出完成记录

**落点按发起方切分（硬性）**：

| 发起方 | 落点 | 记什么 | 编号 |
|---|---|---|---|
| `qiuyuan-guild` | 本仓 `records/` | **跨库任务 + 契约 / 纪律 / 准入变更** | **`X-<编号>`** |
| `qiuyuan-dalu` | `dalu/records/` | 本工程实现任务（写代码 / 做场景 / 配表） | **`T-<编号>`** |
| **向上游提的需求** | **上游自己的**记录体系 | 上游内部任务 | **`U-<编号>`**（见下） |

> **⚠️ 编号空间三条（v0.19 新增第 3 条）**：
> 1. **`X-`** —— 本仓变更，**与 `records/X-*.md` 同号对应**（ledger 索引 ↔ records 正文）。
> 2. **`T-`** —— dalu 工程实现，正文在 `dalu/records/`。
> 3. **`U-`** —— **向上游提出的订正需求**（v0.19 新增）。
>    **为什么必须单开**：这类需求的**正文永远在上游**（铁律一：上游只读，不代写），
>    **本仓永远不会产生 `records/U-*.md`** —— 若沿用 `X-`，就会出现
>    「**同一编号、本仓一篇 `records/` 正文、上游一件事**」的**双义撞号**。
>    **教训来源**：v0.19 实测发生 —— `records/X-0005.md`（UE 工程规格）与 ledger 的 `X-0005`（`exp_required` 作废）**同号不同事**，
>    且 `records/X-0003 ~ X-0006` **四篇正文一直没进 ledger 索引**（违反本文件 5.6「有正文无索引 = 孤儿记录」）。
>    **判据（可迁移）**：**编号空间按「正文落在哪个仓」切分，不按「谁发起」切分。**
>    正文同仓 → 可共用编号；**正文异仓 → 必须分号**，否则索引与正文的一一对应立刻失效。

> **硬判据**：**`records` 必须与它描述的改动同仓。**
> 否则「记录里的改动清单与 git diff 一致吗」这条交叉查账**跨仓失效**。
> 故：dalu 的实现记录**不上移**；guild 的跨库与契约记录**必须有**（契约是会被改的唯一真源，ADR 只记「为什么定」，不记「谁改的 / 验证证据 / 影响面」）。

### 5.2 记录模板

```markdown
# X-0012 <任务标题>（覆盖模块 / 需求来源）

- 状态：已完成 / 部分完成 / 阻塞
- 发起方：<guild | dalu>
- 执行者：<角色>
- 覆盖官方模块：<MMO功能清单 对应项>
- 加载的 skill：<skill 名（来源）>
- 契约引用：<contracts/xxx.md §N / 上游文档>

## 改动清单
- 新增 / 修改 <文件>（<要点>）

## 验证证据（必须可复现）
$ <命令>
→ <实际输出>

## 审核
- 审核者：<角色>
- 结论：**通过 / 不通过**（二值，**不得填分数** —— §5.5）
- 未通过项：<逐条>

## 遗留问题
- <未决项> → 转 <X-xxxx / T-xxxx>

## 执行环境（可选 · 仅供回溯）
- 工具 / 版本：<如 WorkBuddy 1.x>
- 模型：<如 claude-sonnet-4.5>
- 日期：<YYYY-MM-DD>
```

> **「执行环境」节的性质（v0.3 新增 · ADR-0007）**：它是**指纹**，不是**评价**。
> 放**尾部**、**可选**（缺失不构成记录不合格）、**不参与审核 / 不作质量判据 / 不进任何统计**。
> **禁止**据此排序 / 评级 / 比较 agent 或模型。想比较模型 → 走**独立 A/B 实验**（同卡双跑），不在日常记录里做。

### 5.3 证据要求

**「验证证据」必须是命令 + 实际输出**，不是「已测试通过」。**无可复现证据的记录，台账直接驳回。**

### 5.4 索引与正文

- `registry/cross-repo-ledger.md` 是**索引**（一条一行，看全貌）
- `records/X-*.md` 是**正文**（每任务一份，可追责）

**索引给眼睛，正文给审计。** 只留索引 = **只有目录没有内容**。
查账时须**双向核对**：有索引无正文 = 缺账；有正文无索引 = 孤儿记录。

### 5.5 判据形态：**二值判定**（v0.3 新增 · ADR-0008）

**「审核」节只有二值**：`通过` / `不通过`（+ 未通过项**逐条列出**）。**不得出现分数、等级、满意度百分比。**

**禁止「其他 agent 给产出打分」。** 三条理由：

1. **同构互审会放水**（方案 §5.1），而**分数比二值更容易放水** —— 连续量可以「给个面子 8 分」，二值量没有中间地带。
2. **Goodhart 定律** —— 分数一进记录，agent 即为**分数**优化：把任务切碎（个个高分）、把范围写模糊（不易被扣分）。
3. **二值清单是评分的升级版** —— 「135 格，缺 0」没有中间地带。**评分制是审核的降级。**

> **最根本的一条**：四个纵向 agent 是**同一个模型扮的四个马甲**。
> **给马甲排名 = 给同一个模型的四次发言排名。** 无信息量，且会引发为排名优化。

**量化的唯一形式 = 四个客观计数**（由 `ledger` **从 records 统计**，**不新增填报字段**）：

| 计数 | 定义 | 红了说明什么 |
|---|---|---|
| **返工次数** | 同一张卡被退回几次 | 任务卡写不清 / 交接判据缺失 |
| **门禁失败次数** | `check-*.js` 红了几轮 | 契约与产物脱节 |
| **契约变更次数** | 本里程碑改了几次 `contracts/` | **契约没想清就开工** |
| **遗留转出数** | 本卡抛给下一张卡的 TODO 数 | 范围闸门没关严 |

> **这四项是「事实计数」，不是「打分」** —— 且**不可被优化**：想降低返工次数，**唯一办法是别返工**。
> 四项指向**流程环节**，**不指向执行者**。**禁止**据此评价 agent 或个人。

### 5.6 派生视图（v0.3 新增 · ADR-0007）

**「哪个 agent 做了什么」由记录头部的「执行者」字段承担**，不另设真源。

按 agent 看全景 → **派生视图** `registry/agent-log.md`。

| 项 | 规定 |
|---|---|
| **性质** | **视图**，不是第二真源 —— 由 `records/` **派生**，可随时重生成 |
| **判据** | **视图可丢，`records` 不可丢。** 重建视图 = 重跑生成脚本 |
| **禁止** | 不得在视图里**手改**内容（改了下次生成即被覆盖，且制造双真源） |

> **同理**：`registry/cross-repo-ledger.md` 是索引视图，正文永远在 `records/X-*.md`。
> **凡「从别处聚合出来的东西」，一律是视图。**

## 6. 命名与目录

### 6.1 命名形态（四形态各司其职，互不冲突）

| 场合 | 形态 | 例 |
|---|---|---|
| 仓库 / 目录 | **kebab-case** | `qiuyuan-dalu`、`ue-client` |
| UE 工程 / C++ 模块 | **PascalCase** | `QiuyuanDalu`，派生宏 `QIYUANDALU_API` |
| **UE 资产名（`Content/` 内）** | **前缀_PascalCase**（Epic 约定） | `SM_Roof_Xieshan_01`、`WBP_AttributePanel`、`BP_LoginController` |
| **资产源文件 / 生成物（引擎外）** | **kebab-case**（上游 §5.4） | `building-roof-xieshan-01-side.fbx`、`char-npc-merchant-01-base.glb` |
| 契约·实体名 | **单数 PascalCase** | `Role`、`RealmLevelConfig` |
| 契约·字段名 | **snake_case、不缩写** | `realm_id`、`spiritual_root_quality` |
| **数据库表（物理）** | **自由** —— `qiuyuan-dalu` 定，须**全库统一** + `role_id` 一级键 | 原型曾用 `xx_`；需求层无前缀 |
| 契约 / 文档文件 | **kebab-case.md** | `data-contract.md` |
| 展示 / 产品名 | 中文 / 空格 | `虬渊大陆` / `Qiuyuan Dalu` |

> **判据**：**该场合的法定形式是什么，就用什么。** 不要把一种场合的形式套到另一种场合上。
> **改 UE 工程名不动仓库名**（两者是两个场合的两种法定形式）。
> **改表名不动契约**（物理与逻辑是两层，见 §1.2）。

> **资产命名的两条线不冲突**（v0.4 补录 · ADR-0013）—— 判据是**「引擎内 vs 引擎外」**：
> - **引擎内**（`Content/` 里的 `.uasset`）→ **Epic 前缀规范**。因为资产名受**引擎约束**（C++ 类名、重定向器、蓝图引用），改名的代价由引擎决定。
> - **引擎外**（源文件 / 生成图 / AI 批量产物 / 交付包）→ **上游 §5.4 kebab 规范**（`类别-名称-变体-序号`，批次号带 `-b{批次}`）。因为它是**生产管线**的产物，要能被脚本批量回溯与重生成。
> 两者是**同一资产在两个场合的两个名字**，**不是二选一**。完整前缀表见 `PROJECT-STRUCTURE.md` §4。

### 6.2 目录归属

- 本仓（guild）：`docs/` `contracts/` `tasks/` `records/` `registry/` `scripts/`
- 下游（dalu）：`docs/` `tasks/` `records/` `tests/` + 引擎层（`ue-client/` `data/` `server/` `admin/` `db/` `tools/`）
- **`data/` 放 dalu 的 repo 根，不放 `ue-client/` 内** —— 因为**服务端与客户端要读同一份配置表**。只放客户端，服务端就得另存一份，**双真源当场成立**。
- **dalu 不建 `contracts/`**（真源在本仓，本地副本 = 分叉的路）。

### 6.3 写权边界

**一列一主**：同一时刻同一目录只有一个 agent 有写权。

- **纵向 owner 独占写权**（模块领地）
- **横向职能只读**（review / qa / ledger / arch）—— 发现问题**回交 owner**，不自己动手
- 服务端加入后，边界**下沉到模块子树**：`world` = `data/` + `server/internal/world/` + `ue-client/…/World/`；其余同理

> **横向越权是唯一的硬红线。**

## 7. 门禁与校验

### 7.1 校验脚本

```bash
node scripts/check-data.js        # 契约 ↔ 配置表 + 文档表格结构 + 第一原则锚点（9 规则 R1~R9）
node scripts/check-data.js --self-test   # ★ 反向测试：注入坏样本，断言必失败
node scripts/check-asset-ref.js   # 场景引用 ↔ 资源清单 ↔ 实际资产（5 规则）
node scripts/check-interfaces.js  # 跨模块接口 ↔ 契约（待建）
```

> **没有校验脚本的契约 = 装饰品。**

**六条脚本编写纪律**：

1. **禁止「空集真空通过」。** 若解析不到任何待校验项，**必须报错**，不能静默通过。
   > 实例：`check-asset-ref.js` 初版截取段落时只截到首个空行，分类表没进解析范围 → 空集 → 显示「全部命中」。**比报错更危险**，因为它给了虚假的安心。
2. **每条规则必须有反向测试。** 没失败过的校验脚本 = 未被验证过的校验脚本。
   > 实例：`check-data.js` 初版 `R1` 漏了正则 `m` 标志、`R3` 切分粘连 —— 都是**跑第一次才暴露**。
   > **进度（v0.17）**：`check-data.js` **已实现 `--self-test`**（**27 个用例**，覆盖 R2 / R5 / R7 / R8 / R9 的坏样本与好样本）。**`check-asset-ref.js` 仍待补。**
3. **契约改了，脚本必须同批改**（v0.14 新增）。
   > 实例：v0.14 改契约后复跑，发现 `R2` 还在钉已作废的 `0~8`、`R6` 还在**强制** `xx_` 前缀（**直接违反刚立的 ADR-0001**）、`R5` 漏掉「待确认 / proposed」等写法。
   > **这三条都不是报错，而是「看起来通过了」** —— 与纪律 1 是同一类病：**虚假的安心**。
   > 判据：**改完契约，必须复跑脚本并核对每条规则的「语义」是否仍然成立**，不只看红绿灯。
4. **断言不得依赖会过期的魔法数字**（v0.15 新增）。
   > 实例：`R5` 初版写 `EXPECTED_FLOOR = 3`（按"已知 3 条 ADR 待裁"设的下限）。**ADR 一裁定，这个数字立刻失效** —— 规则会从"防漏报"变成"永远误报"。
   > **正解**：改为**与真源联动** —— `R5` 现直接读 `docs/DECISIONS.md` 数 `proposed` 条数，与契约里的待裁项**交叉核对**。
   > **判据**：**凡是断言里写死的"当前有 N 条/X 个"，都在给未来埋雷。** 能从真源算出来的，就不要写死。
5. **文档结构也是交付物**（v0.16 新增）。
   > 实例：`ROADMAP.md` §1 总表的 M2~M17 行把「依赖」值填进了「状态」列。**列数恰好齐**（尾部空单元格补齐，5 列 = 5 列），
   > 所以任何「数管道」的检查都放行 —— 最后由**大人在 Obsidian 里肉眼发现**。这是**门禁缺位**，不是运气不好。
   > 由此新增 **`R8`**：① 表格前一行须空行（err，否则 markdown-it 不渲染）；② 列数须与表头一致（err）；③ 行尾空单元格（warn，疑似列位错填）。
   > **判据**：**列数一致 ≠ 列位正确。** 凡是「人能一眼看出、脚本却不报」的，都是门禁缺口 ——
   > 要么补规则（首选），要么**显式登记为人工检查点**（并在 `records/` 中留痕）。**不许既不补规则、又不承认它是人工项。**
   > **登记落点** → **§7.4 人工检查点登记表**（v0.17 新建）。
6. **语义判断不得硬写成脚本**（v0.17 新增）。
   > 实例：第一设计原则的三问（世界观依据 / 感知路径 / 删除测试）—— 脚本只能查「**有没有填**出处」这种**形式**，
   > 硬写成规则会催生**填假出处**（形式合格、内容造假）。
   > **正解**：**可机械校验的**（锚点存在性 → `R9`）写成脚本；**须人判的**登记为人工检查点（**§7.4**）。
   > **判据**：**凡「脚本能判的」与「脚本假装能判的」混在一起，后者一定退化成虚假的安心。**

### 7.2 「上下文不是配置」——规则分两级

| 级别 | 载体 | 适合 |
|---|---|---|
| **文档级（提醒）** | `AGENTS.md` / `CONVENTIONS.md` 里的句子 | 「我们一般这么做」 |
| **门禁级（强制）** | hook / 校验脚本 / 权限 | 「无论如何都必须」 |

> 规则文件是**作为消息投递给模型**的，模型「读到并试图遵守」，**没有任何保证**。
> **判据**：**同一个规则在文档里写了三遍还不被执行，它就该做成门禁，而不是再写第四遍。**

**门禁时机**：**Phase 1 就上最小门禁**（一个 pre-commit 钩子 + 一个校验脚本）。纯文档规则会被静默忽略。

### 7.3 skill 准入

skill 是**可执行的指令 + 脚本**，能碰文件系统与密钥 —— **它不是文档，它是依赖**。

- 多渠道来源（hub / GitHub 仓库集合 / 开放注册表）**一律先隔离、审计、vendor 进仓库、再使用**。
- **vendor 进仓库不引外部路径** —— 上游一删就断供，云电脑拉不到。
- 审计结论分级：**P0 不装** / **P1 须明确确认** / **P2 可装**。
- 本仓负责**准入规范与缺口登记**，**不代替执行方做内容**。

### 7.4 人工检查点登记（v0.17 新增）

> **缘起**：§7.1 纪律 5 要求 —— 凡是「人能一眼看出、脚本却不报」的，**要么补规则（首选），要么显式登记为人工检查点**，不许两者都不做。
> **但登记表此前并不存在** —— 于是「显式登记」无处可落，实际等于**没登记**。本节补上这个落点。

**判据**：一条规则该不该做成脚本，看它的判据是**机械可比**还是**须语义判断**。

| 判据类型 | 处置 | 例 |
|---|---|---|
| **机械可比** | ✅ 写成校验脚本（首选） | 「契约里有没有物理表名」（`R7`）、「表格列数与列位对不对」（`R8`） |
| **须语义判断** | ⚠️ **登记为人工检查点**，由指定角色在指定环节判定 | 「这个设计是否忠于世界」（第 1 号） |

**禁止**：把语义判断**硬写成脚本** —— 脚本只能查**形式**，会催生**形式合格、内容造假**（填假出处、凑字数的答案）。这是**虚假的安心**，与 §7.1 纪律 1 同一类病。

#### 登记表

| # | 检查点 | 判据 | 判定角色 / 环节 | 判定形态 | 登记于 |
|---|---|---|---|---|---|
| **1** | **世界真实性三问** | ① 世界观依据（出处具体到页）② 感知路径（不得仅靠面板数字）③ 删除测试（失去的是「体验」而非「功能」） | 任务卡**发起人**自答 → **L1 / L2 审核者**判 | **二值**（通过 / 不通过 + 逐条未通过项），**不得评分**（§5.5） | ADR-0009 / 方案 §0.0 |
| **2** | **范围闸门是否关严** | in / out 两张清单是否写明；out 的项**是否被「顺手做了」** | 同上 | 二值 | ADR-0003 / 方案 §9 |

> **第 1 号的适用范围**：**新系统 / 新玩法 / 新功能**。**纯重构 / 修 bug / 排版类不适用** —— 否则会退化成形式主义填表。
>
> **登记表自身的维护**：新增人工检查点**必须**在此登记，并注明**判据**与**判定角色**。
> **没登记 = 没这项检查** —— 它会随着上下文被替换而静默消失。

## 9. 环境与版本锁定（v0.4 新增 · ADR-0012）

**真源**：**`docs/ENVIRONMENT.md`** —— 本项目「用到的应用 + 锁定版本 + 实测现状 + 校验命令」的**唯一真源**。
**本文件与其它文档一律指针引用，不复写任何版本号。**

> 判据：**同一事实不写两处 = 迟早不一致。** 版本号是**最容易腐烂**的一类事实 —— 装一次就变，抄多处必错。

**三条铁律**（详见 `ENVIRONMENT.md` §0）：

| # | 铁律 | 反面教训 |
|---|---|---|
| 1 | **唯一真源** —— 版本号只在台账维护 | 环境事实曾抄在 `PROJECT-STRUCTURE.md` §3.1，与台账并行维护 |
| 2 | **现状只写实测** —— 不得由安装记录 / 版本号外观 / 目录名推断 | 「**装了 ≠ 能用**」／「**目录名不是版本号**」（MSVC 误报两次） |
| 3 | **版本变更须 ADR** —— 升级 / 降级 / 换选型均先落 ADR | 与本节所属文件的「升版规则」一致 |

**为什么「UE 版本必须全队锁定同一小版本」**：
UE 的**小版本之间不保证资产兼容** —— `5.8.1` 存的 `.uasset` 被更高补丁版打开会**静默升级且不可回退**。
故**开发机 / CI / 任何 agent 环境**都锁定同一版本（锁定值见 `ENVIRONMENT.md` §2.1）。

**装机后的义务**：新装工具（Go / protoc / Luban 等）**当场回填台账**（锁定值 + 现状 + 校验命令实际输出），
**不许「装了但没记」**—— 那等于台账失效。
