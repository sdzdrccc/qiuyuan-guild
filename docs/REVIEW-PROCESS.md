## 0. 一句话

**审阅 = 用「可复现的证据」回答「这些产物到底对不对」，产出二值判定与分层归属。**

一条可复用判据（`X-0015` §遗留）：

> **规则写了不执行，等于没写；执行了却没人看得见，等于半写。**

**两条元判据**（`X-0018` 补 · 审阅自身的纪律）：

> ① **审阅也会错** —— 审阅者自写的脚本**同样要过「反向测试」**；
>    当它**与门禁冲突**时，**先怀疑自己**（先例：审阅者的临时脚本把 3 笔合规提交误判为违规，门禁是对的）。
> ② **审阅自己的结论也要能被复核** —— 所以每条结论必须带**命令 + 实际输出**，
>    且**声明没覆盖什么**（§3 第 1 步 / §4 模板）。

## 1. 什么时候要审

| 触发 | 例子 |
|---|---|
| **一个波次 / 里程碑做完** | M1 波次 1 做完 → 审 |
| **跨仓交付前后** | dalu 交付 → guild 审 |
| **契约或门禁被改** | 改 `contracts/` 之后 |
| **大人点名** | 「审一下 `X`」 |

> **不审的情形**：纯排版 / 错别字 / 单行修 bug —— 走正常门禁（`check-*.js`）即可，不必起审阅。
> 审阅的成本在**第 4 步**（逐条复现证据），别把它浪费在不必逐条的地方。

## 2. 审谁 · 谁是审阅者

**核心问题（方案 §5.1）**：**agent 审 agent 会互相放水** —— 同一模型、同构盲区，A 写 B 审，B 大概率看不出 A 的错。**不是态度问题，是能力同构。**

**破解（方案 §5.2）**：**审核者必须是「下游消费者」**。

| 产物 | 审阅者 | 判据 |
|---|---|---|
| `world` 的配置表 | `combat` + `ui` | 它们要读这份数据，**读不通立刻暴露** |
| `combat` 的接口 | `ui` | UI 要调它 |
| `scene` 的场景 | `asset`（尺寸 / 锚点）+ `qa` | 资产要装进场景 |
| **`contracts/` 的契约** | ★ **下游（`qiuyuan-dalu`）** | 「下游读不通」= **契约缺东西**（机制⑦ 契约回执） |
| **跨库 / 跨里程碑的整批交付** | **`review`（横向职能）+ 大人** | **本流程** |

> **一句压过一百句**：**「这个字段我读不到」比「这个设计不好」有力一万倍。**
>
> ★ 第三行此前**方案里没有**（`X-0015` §五-⑦ 的真空）—— 补法就是机制⑦：**让下游每张卡自动上报**。

## 3. 六步流程

### 第 1 步 · 定对象与范围（写死）

- 明确：**哪个仓、哪几笔提交 / 哪个里程碑**。
- **记下审阅快照**（两仓 HEAD 的短 hash）—— 它标识**本次审阅看到的是哪个时点**（§5-纪律 3）。
- ★ **同时声明「本次不覆盖什么」** —— 见 §4 模板的「本次未覆盖」节（`X-0018` 补）。
  实证：`X-0015` 那次**没审** `ue-client/` 的 C++、`admin/`、UE-MCP 链路，**但一处都没写明**，读者容易误读为「全审了」。
- 产出：**可复现的审阅对象**（提交范围 + 快照 + 未覆盖清单）。

> ⚠️ **两个「纪元」不是一回事**（`X-0018` 补 · 实测混用风险）：

| 概念 | 在哪 | 谁能改 |
|---|---|---|
| **① 门禁基线 `GATE_EPOCH`** | **脚本内**（`check-records.js`）· 单一值 | ★ **冻结不动** —— 移动须**落记录 + 大人裁**；**推进 = 存量被洗白**（`C7` **err**）· **回拨 = 变严**（存量转新增 · `C7` **warn**，须落记录） |
| **② 审阅快照** | **记录头部**（本次审阅的两仓 HEAD） | 每次审阅各写一份，**只标识范围，不参与门禁判定** |

> **判据**：①是**门禁的锚**（决定「谁算存量」），②是**审阅的坐标**（决定「这次看的是哪一刻」）。
> 把②当成①来写（例如为了让自己这次干净而推进 `GATE_EPOCH`）= **洗白存量**。

### 第 2 步 · 收集判据（**不自造**）

| 判据来源 | 拿什么 |
|---|---|
| `docs/ROADMAP.md` | 该里程碑的 **in / out scope** + **出口判据** |
| `contracts/` | 涉及的实体 / 字段 / 公式定义（**真源**） |
| 方案 §5.3 | 该改动该给什么**级别**（L0~L3） |
| `docs/CONVENTIONS.md` | 命名 / 数据 / 记录 / 门禁 约定 |
| `scripts/check-*.js` | **可机械执行**的那部分（清单见第 3 步 · 由 `D1` 锚定） |
| 上游三库（`虬渊大陆` / `gbe-*`） | 数值与设定的**真源**（**只读**） |

> **纪律**：**审阅不自造判据** —— 每条判据都必须能**指回某一处真源**。
> 判据自造的审阅，等于给被审者换了一套考试题。

### 第 3 步 · 先跑机械判据（能脚本判的，不动嘴）

```bash
# 门禁（guild）—— 每个都可加 --self-test（反向测试）
node scripts/check-data.js            # R1~R10
node scripts/check-contract-gate.js   # G1
node scripts/check-identifiers.js     # I1
node scripts/check-records.js         # C1~C9
node scripts/check-doc-anchors.js     # D1~D5
node scripts/check-asset-ref.js       # A1~A5
node scripts/check-version-pins.js    # P1~P5（版本配套表 ↔ 契约版本）
node scripts/check-docs-index.js      # E1~E3（docs/ 顶层索引覆盖率）

# 被审仓（如 dalu）
go build ./... && go vet ./...
bash data/gen.sh && git status --short data/gen server/internal/platform/config/gen   # 生成链路幂等
mysql -u root -e "..."                # 落库实测（字段 / 索引 / 注释 / 编码）
```

> ★ **纪律**：**「跑完没报错」≠「对了」** —— 见 §6 坑 1。
> 零报错的静默损坏（CSV 截断 / 编码乱码）**只有靠结构核对才能抓到**。

> ★ **`--strict` 怎么用**（`X-0018` 补 · 此前未定，审阅者会各发明一套）：
> **审阅用「常规模式」** —— **存量 `warn` 不构成「不通过」**，但**必须逐条进 §六 存量清单**（可见不掩盖）。
> `--strict`（警告即失败）**留给 CI / 提交前**，不用于审阅判读。

### 第 4 步 · 逐条给可复现证据

- 每条结论 = **命令 + 实际输出**，不是「已检查」/「已测试」（`CONVENTIONS.md` §5.3）。
- **不盲信上游审阅**：上游说的每一条，**自己复跑一遍**再采信。
- ★ **数值 / 统计类结论必须「独立复算」，不是「复跑」**（`X-0018` 补）：

  | 手法 | 做什么 | 能抓到什么 |
  |---|---|---|
  | **复跑** | 再跑一遍**对方给的脚本** | 抓「当时环境不对 / 没跑全」 |
  | **独立复算** | **按真源自己重写一遍**（可换 RNG / 换实现） | ★ 抓「**对方的脚本本身错**」——复跑抓不到 |

  **实证**：本项目在数值上正栽过一次 —— `v0.5` 自称「期望恰 `1.0000`」，实测 `1.162`；
  **只有另写一遍才能发现**。审阅 `X-0015` 时即换 RNG 自写 100 万次。
  **判读法**：口径 / RNG 不同 ⇒ **只验统计量**（期望 / 区间 / 单调 / 越界），**不逐位对齐**。
- ★ **「修好了某类环境问题」须做「反事实复验」**（`X-0018` 补 · §6 坑 1 的解法）：
  在该问题的**恶劣条件**下复跑 —— 编码（敌对 `--default-character-set`）、大小写敏感、CRLF、并发。
  **实证**：证明「修中文乱码」是**根因修复**而非「当前环境恰好没坏」，靠的是**用 gbk 删库重建**后注释 HEX 逐字节不变。
- 判定 **二值**：`通过` / `不通过` + **未通过项逐条**。**禁评分**（ADR-0008 · §5.5）。
- **门禁的红，是结论不是故障** —— 红着是因为**它抓到了真问题且还没修**；**修好之前，红就是对的状态**（绿灯才是虚假的安心）。

### 第 5 步 · 归类 + 产记录

- **分层归属**：
  - **下游改**（本仓 / dalu 内部能修的）→ 开 `T-*` 或直接修；
  - **上游改**（要动契约 / 世界观 / GBE）→ **开 ADR + 跨库台账**，**不代写**（铁律一）。
- 产 `reviews/X-00NN.md`（guild 侧）或转 dalu `T-*`。
- 登记 `registry/cross-repo-ledger.md`（索引 ↔ 正文双向核对）。
- **审核节**填**触发级别**（改契约的必须 **L3 = `arch` + 大人**）。
- ★ **契约回执要「读」**（`X-0054` · G-3 补）—— 此前只判「有没有这一节」，回执里写的「哪一处读不通」没人消费。
  现由 `check-records.js` 的 **`C6`** 把回执内的「读不通 / 缺定义 / 需变更」要点**捞出来并列条**；
  **`arch` 每周**把该清单汇总进 `registry/cross-repo-ledger.md` 的验收结论区 —— ★ **只收不回 = 没这一步**。

### 第 6 步 · 复审与销号（`X-0018` 补 · **此前完全缺失**）

> **缺口实证**：此前的五步流程覆盖「审 → 产记录」，**没有一步说「修完之后怎么办」**（故补本步）。
> `X-0015` 状态长期停在 `待验收`，而 dalu 已修 6 处、门禁已转绿 ——
> 实际是靠「**又开一篇 `X-0016`**」承担，属**流程外自发**。

**销号的三个条件**（缺一不可）：

| # | 条件 | 判据 |
|---|---|---|
| ① | **逐条复跑原证据** | 原记录「未通过项」**每一条**都附复跑输出 —— **不是「对方说修了」** |
| ② | **门禁转绿** | 相关 `check-*.js` 由红转绿（或**写明为何该红**—— 例如「属上游待裁，非本仓可修」） |
| ③ | **只追加** | 销号写在**新记录**里，**不改原记录**（历史条目一个字都不许改） |

**部分转绿怎么办**：记录里**分别列「已销 / 未销」** —— 不许笼统写「已修复」。
**状态流转**：`registry/cross-repo-ledger.md` 该行 `待验收 → 已关闭`，且**销号记录须指向原记录**。

> ★ **销号不是「重新审一遍」** —— 只复跑**原记录的未通过项**；若修复本身引入新面，**另开一次审阅**。

#### 销号有**两条路** —— **先看判据，再看豁免**（`X-0019` 补 · 实战一次销 35 项）

| 路 | 何时用 | 代价 / 边界 |
|---|---|---|
| **① 判据修正**（★ **首选**） | 存量项是**判据过宽造成的误报** | 改对了**永久消失**；**拿豁免盖住 = 同类误报下次照来** |
| **② 留证豁免**（次选） | 确属**机制建立前**的存量，且**回填历史会造假** | 须写进 `WAIVED` 花名册，**三个命名空间**：`commits` / `sections` / `records` |

- **豁免三要件**（缺一不可）：**依据 + 裁定人 + 日期**；`sections` 命名空间**只对软性节**适用。
- **打印要求**：豁免须**归组打印** —— 既点名（谁被豁免）又不淹没（不逐条刷屏）。
- ★★ **不回填历史** —— 回填 = **造假**；存量与新增必须分开算（§5 纪律 3）。
- ★★★ **「补记」消不掉判据对【那笔提交】的红**（`ADR-0024` 补 · 实证 `C5`）——
  提交级判据（如 `check-records.js` 的 `C5`）判的是「**那笔提交的文件列表里**有没有同时含实现文件与记录文件」
  （**同一提交内**），⇒ ★ **事后另开一笔提交补记录，对历史那笔的判定毫无影响**。
  - ★ **正确认知**：`C5` 报 err ⇔ 「**那笔提交当时没带记录**」，★ **不是**「现在查不到记录」。
  - ★ 实证：`daa6763` 在**删掉违规文件后依然报 err**（`T-0028:150` 早已写下「删文件改不了历史」）。
  - ⇒ ★ **真缺记录**就**另写记录**；★ **已补记的**走「**留证豁免**」—— ★★ **但先查豁免表对不对该判据生效**
    （`C5` 曾长期只对存量查豁免、不查新增 ⇒ **已补记的和真没记录的长得一样**，**读门禁的人分辨不出**）。
- ★ **不能派生的计数不要填 `0`** —— `0` = 声称「**从未发生过**」，比留空**更危险**。
- ★ **销号 ≠ 复核通过** —— 原记录 §审核 若仍写「待复核」，**照样留着**，销号只解决「遗留项」。
- ★ **销号记录可兼作原记录遗留项的销号**；此时**原记录只追加指针**（守「只追加」）。

#### ★★ 「授权 ≠ 点头」（`X-0019` 补 · 实证 `X-0018` 遗留 7）

原记录里写「**请大人确认**」的项，**不因**「遗留问题已全部解决」这类**笼统授权**而自动关闭。
关闭须三步：**① 按授权推进 ② 保留回退条件 ③ 显式请裁** —— 待大人**明确答复**才解除。

> 反例：把「大人说『遗留问题全部解决』」当成「大人同意关闭那一条」= **替大人做了他没做的决定**。

## 4. 输出格式

审阅记录 = `CONVENTIONS.md` §5.2 模板的**扩展**：

```markdown
# X-00NN <被审对象> 审阅 —— 缺陷清单 · 变更包 · 门禁落地

- 状态：已完成（审阅 + 门禁落地；待大人复核）
- 发起方 / 执行者（`review`）/ 覆盖官方模块 / 契约引用（只读消费）
- **审阅快照**：guild `<hash>` ／ dalu `<hash>`   ← 仅标识**本次看到哪一刻**（≠ 门禁基线，见 §3 第 1 步）

## 一、审阅对象与判定         ← 二值表（审阅项 | 判定 | 依据）
## 二、缺陷清单               ← 每条给**可复现证据**（命令 + 实际输出）
## 三、契约变更包             ← 待落 ADR 的（**全是大人已裁定的口径，只是没同步进契约**）
## 四、门禁落地               ← 新增 / 改的脚本 + 规则 + **反向测试数**
## 五、流程完善提案           ← **未改真源**，待大人裁
## 六、存量清单               ← 门禁报出的 `warn` · **不掩盖**，逐条列出
## 七、可复现验证证据         ← 命令 + 输出（可直接粘去复跑）
## 八、改动清单               ← 文件 | 动作 | 要点（+ **未改真源**的显式声明）
## 九、审核                   ← 触发级别 / 审核者 / 结论 / 未通过项
## 本次未覆盖                 ← ★ **必填**（可写「无」）—— 没审什么，防读者误读为「全审了」
## 遗留问题                   ← 逐条给**去向**（本仓 / dalu / 上游 / 待裁）
## 执行环境（可选 · 仅供回溯） ← 工具/版本 + **模型** + 日期
```

> **「本次未覆盖」节（`v1.2` 新增 · `X-0018` · 由 `check-records.js` **`C8`** 兜底）**：
> **必填**，可写「无」。它**只对审阅类记录**强制（大标题形如 `<对象> 审阅 —— …`；
> `审阅流程化` / `审阅模板补节` 这类**流程建设**记录不适用）。
> **为什么值得一条门禁**：`X-0015` 那次没审 `ue-client/` 的 C++、`admin/`、UE-MCP 链路，
> 而记录里**一处都没写明** —— 读者会把「审过一部分」读成「全审过」。
> ★ **防假通过**：门禁认的是**节**，不是正文里出现「未覆盖」四个字。

> **销号类记录**（§3 第 6 步）建议另起模板：`# X-00NN <原记录> 销号 —— 逐条复跑结果`，
> 正文只写 **原未通过项 × 复跑输出 × 已销/未销**，并在尾部指向原记录。

> ⚠️ **`C4` 的已知误报源**（`X-0018` 补 · `X-0016` §七 即先例）：
> `C4` 的「涉契约」判据是**文本命中**（正文出现 `contracts/`）—— 于是
> **「只读消费、不改契约」**的记录也会被要求 **L3**。
> **处置**：**按实际改动面定级**，并在审核节注明「`C4` 判据为文本命中，实为引用」。
> **禁止为了过门禁而顺手填一个 `L3`** —— 那是 ADR-0008 反对的「为填而填」，
> 且会让「分级」这个字段失去信息量（**全部 L3 = 没有分级**）。

> **「执行环境」节的性质（`v1.1` 新增 · 对齐 `CONVENTIONS.md` §5.2 / **ADR-0007**）**：
> 放**尾部**、**可选**（**缺失不构成记录不合格**）、**不参与审核 / 不作质量判据 / 不进任何统计**。
> 记三样：**工具 / 版本** · **模型** · **日期** —— 目的是**回溯**（当时是什么环境跑的），**不是评价**。
> ★ **禁止**据此**排序 / 评级 / 比较 agent 或模型**。四个纵向 agent 是**同一个模型扮的四个马甲**，
> 给马甲排名 = 给同一模型的四次发言排名 —— **无信息量，且会引发「为排名优化」**。
> 要比模型 → 走**独立 A/B 实验（同卡双跑）**，不在日常记录里做。
> 门禁**刻意不校验**本节在场（`C1` 只查「状态 / 执行者」）—— 与「可选」的定义一致。
>
> **与「执行者」的分工**：**「谁审的」看头部 `执行者`**（**必填** · `C1` 兜底）；
> **「什么环境审的」看本节**（**可选** · 不兜底）。二者**都不是**质量判据。

## 5. 五条设计纪律（`X-0015` 实测踩出来的）

1. **误报率高的门禁 = 没有门禁。**
   收紧到**高信号命名空间**（如 `qydl_*` / `*_ppm` / `*_config`），并**排除 `records/`**（历史留痕按纪律「只追加不改写」，本就该保留旧名）。
   → **宁可漏报，不可误报** —— 这是**自觉的取舍**，不是能力不足。

2. **脚本别假装能判语义。**
   能判的（锚点存在性 / 列数 / 单调性）→ 写脚本；**须人判**的（是否忠于世界 / 范围闸门）→ **登记为人工检查点**（§7.4）。
   → **凡「脚本能判的」与「脚本假装能判的」混在一起，后者一定退化成虚假的安心。**

3. **存量与新增必须分开算。**
   以 **`GATE_EPOCH`** 为界：**之前 → `warn`**（并**逐条列出**，可见不掩盖）；**之后 → `err`**（必须办）。
   → 否则门禁一上线就**永久红** = 被无视。
   → **豁免也要留证**：写进 `WAIVED` 花名册（**理由 · 裁定人 · 日期**），与 `RETIRED`（退役名花名册）同构。
   → ★ **但基线本身「冻结不动」**（`X-0018` 补 · 见 §3 第 1 步的两纪元表）：
     **推进**基线 = **洗白存量**（`check-records` **`C7`** 会 **err**）；
     **回拨**基线 = **变严**（存量突转新增，须**落记录 + 大人裁** · `C7` 报 **warn**）。

4. **审阅者自写的工具，同样受门禁约束**（`X-0018` 补）。
   审阅时会写一次性脚本（复算 / 统计 / 比对）—— 它们**也要过反向测试**这一关，
   否则审阅者会用自己的错判据去否定被审者。
   **实证**：审阅 `X-0015` 时，审阅者的临时脚本把 **3 笔合规提交误判为违规**（漏了「同批记录」判定），
   **门禁是对的**。⇒ **冲突时先怀疑自己**，并给出可复核的判据（取文件**首次出现**提交 / 逐笔 `git show`）。

5. **「独立复算」与「复跑」是两件事**（`X-0018` 补 · 详见 §3 第 4 步）。
   复跑抓「环境不对」，**独立复算**才抓「**对方的脚本本身错**」。
   数值 / 统计类结论**一律走独立复算**。

## 6. 坑（实战 · 全部踩过）

1. **「跑完零报错」≠「对了」。**
   - CSV 一个未转义逗号 → Luban **零报错**把「可行域上界」**静默截断**；
   - Windows `mysql.exe` 默认 `character_set_client=gbk` → UTF-8 脚本**零报错**但中文注释**全乱码**。
   → 判据必须是**原始字节 / 结构核对**（`HEX(TABLE_COMMENT)`、**字段数 vs 表头列数**、`information_schema` 逐项比对），**不是**「命令 exit 0」。
   → ★ **解法是「反事实复验」**（`X-0018` 补）：在该问题的**恶劣条件**下复跑 ——
     `--default-character-set=gbk` / 全小写文件名 / CRLF / 并发。**没在恶劣条件下跑过的修法，只是「当前环境恰好没坏」。**

2. **人工清点引用面会漏。**
   改名后「**同义但换了写法**」的表述清不到（曾自称「21 处已清」，实际有漏网）。
   → 靠门禁（`check-identifiers.js` **`I1`**），**不靠人眼**。

3. **「改了文件」≠「新增」。**
   判存量 / 新增要取**文件首次出现**的提交（`git log --diff-filter=A`）。
   取「最后一次改动」会把「**老卡被顺手改一行**」误判为新增（**实测**：`T-0010` / `T-0017` 因修一处引用而从 `warn` 变 `err`）。

4. **契约与实现脱节，往往没人发现。**
   `X-0015` 的实测：guild 的契约与门禁**落后下游一整天，无人察觉**。
   → **机制⑦ 契约回执**把它前置化：下游每张卡自动上报「哪一处读不通」，不必等审阅。

5. **别用 `site:` 外网检索代替**站内检索**（判断某平台「有没有」某类资源时）。**
   曾据此断言「hub 无游戏开发类 skill」，实际有 —— **结论性判断必须附检索记录留证**。

6. **审阅的边界会「膨胀」**（`X-0018` 补）。
   从「读一个仓」很容易一路查到另一个仓的 CSV 逗号、DB 编码、面板缺来源 —— **本轮实测就走完了这条路**。
   → **纪律**：**发现即登记，不就地扩审**。超出第 1 步写死的范围的，一律进「遗留问题」给去向，
     下一轮另开审阅；**否则审阅永不完结，且结论与最初判据脱钩**。
   → 与之配套的是 **「本次未覆盖」必填**：**范围写明了，膨胀才看得见**。

7. **文档与脚本之间会长出「没有锚的接口」**（`X-0018` 补）。
   `REVIEW-PROCESS.md` 自述与 `CONVENTIONS.md` / `AGENTS.md` 同级，却**没有任何门禁引用它**；
   实测 `D1` 一上线就抓到 `CONVENTIONS.md` 列了**不存在的** `check-interfaces.js`。
   → 靠 `check-doc-anchors.js`（**`D1`~`D5`**）钉住：脚本清单 / 规则 ID / skill 版本 / README 禁抄版本号 四处同步。

8. ★ **「判据反向」比「判据过宽」危险得多**（`X-0018` 复核发现）。
   **判据过宽**会**误报** —— 你**立刻**知道它坏了（本仓自纠的 5 处**全是这一类**）。
   **判据反向**会**一直绿灯** —— 它把「危险」判成「正常」、把「正常」判成「危险」，
   **只有独立推理（另写一遍判据）才发现**。
   实证：`C7` 首版按「**回拨** = 洗白存量」实现，而 `epochSet(ep)` = `git rev-list ep` = 纪元**之前**的集合，
   语义**恰好相反** —— 于是它**放过了真正会洗白存量的方向**，且每次跑都打印「✓ 纪元单调性成立」。
   ⇒ 正是纪律 2 说的「**虚假的安心**」—— **红灯你怕，一直绿灯的错判据你根本不会看**。
   → **对策**：新增或修改**任何**判据后，自问 **「它把什么判成通过？那个东西真的该通过吗？」**；
     并**必须补一条「反向用例」** —— 断言「**不该通过的情形确实不通过**」，
     而不只是断言「该通过的通过」（后者对反向判据**永远为真**，测不出来）。

9. ★★ **门禁失效有「三种」，不是两种**（`X-0022` 补 · 与坑 8 并列）。
   **过宽 → 误报**（你**立刻**知道它坏了）· **反向 → 假绿**（一直绿灯，只有独立推理才发现，见坑 8）
   · **未覆盖 → 静默**（**既不报错、也不绿灯 —— 它根本就没去看那个目录**）。
   实证：`check-data.js` 的 **`R8`（Markdown 表格结构）只扫 guild 仓** ——
   **`qiuyuan-dalu` 的 `docs/` / `records/` 不在其内** ⇒ dalu 侧 **5 处表格竖线缺陷无门禁可拦**
   （2 处新引入 + 3 处存量），**只能靠人工撞见**；而**同一批文档在 guild 侧跑 `R8` 是全绿的**。
   → 三类对照：**过宽看得见 · 反向看不见 · 未覆盖根本没看**。**未覆盖最容易被误当成「全绿」。**
   → **对策**：读任何绿灯前，**先问「它的扫描范围包含我要保护的那个目录吗？」**；
     **新增 / 修改 / 扩域判据后必须补「覆盖用例」** —— 断言「**目标目录确实被扫到**」
     （只跑「本仓绿」**证明不了**跨仓、子目录被覆盖 —— 绿灯可能只是**没扫**）。
   → ★ **处置原则**：**单仓门禁只管本仓** —— 让上游门禁去扫下游仓，等于**上游依赖下游的存在**，
     破坏「规范中枢不依赖执行仓」的边界。**正确做法 = 下游自建同判据的脚本**（`X-0022` §遗留 1）。

## 7. 怎么让别的 agent 执行（本流程的用法）

> **硬要求**：无论谁来执行 —— **判据不自造**（§2）、**证据可复现**（第 4 步）、**判定二值**（§5.5）。

## 9. 审阅文档存放（★ 唯一目录 · 2026-10-01 统一）

> **一句话**：**审阅相关文档只有一处 —— `qiuyuan-guild/reviews/`。**
> 此前审阅记录在 `records/`、而外部报告散在被审仓的 `docs/` 里 —— **读者要猜去哪找**。

### 9.1 目录约定

| 位置 | 放什么 | 谁产 |
|---|---|---|
| `reviews/X-00NN.md` | ★ **判定正本** —— 本仓发起 / 执行的审阅记录（**与 `registry/cross-repo-ledger.md` 同号对应**），**一号一卡一台账** | guild（`review` 职能 / 主 agent 汇编） |
| `reviews/work/<来源>-<对象>/` | ★ **内部源材料**（`v1.8` 新增 · `ADR-0032`）—— **本仓派出去的每个 agent 各出一份独立报告**，**原样收录**（供横向对比） | 本仓派出去的 sub-agent |
| `reviews/ext/<来源>-<对象>/` | **外部源材料** —— **非本仓派出**的审阅报告（第三方工具 / 别家 agent），**原样收录** —— ★ 一个「来源 ＋ 对象」一个目录，报告按日期累积（**旧目录不回填** · §9.2 纪律 2） | 外部 |
| `reviews/INDEX.md` | 总索引（**视图** —— 由 `reviews/` **目录内容**派生，可重生成，**不是第二真源**） | 脚本 / 人 |

> ★★ **判据（`v1.8` · `ADR-0032`）—— 两问一刀，别再按「来源」猜**：
> ① 这份文档是「**判定正本**」还是「**源材料**」？ 正本 ⇒ `X-*`；源材料 ⇒ 进 ②。
> ② 源材料的作者是「**本仓派出去的**」还是「**非本仓派出去的**」？ 本仓派 ⇒ `work/`；非本仓派 ⇒ `ext/`。
> ★ **只按「谁派的」判，不按工具品牌判** —— 大人派的（哪怕用的是别家产品）也进 `work/`。
> ★ **两档源材料的公共硬约束**：**H1 不得以 `X-` 开头**（`X-*` 只属正本）、**必须自报来源 / 模型**、**只读**。
> ★ **收件说明 ＋ 头部骨架 ＋ 可整段复制的派活指令：`reviews/README.md`**（活模板）。

### 9.2 三条纪律

1. ★ **审阅文档只此一处。** 收到源材料时**移入** `reviews/work/`（**本仓派出去的**）或 `reviews/ext/`（**非本仓派出去的** —— §9.1 的**两问一刀**）；原处（被审仓）**最多留一条指针**，不留正文。
   —— 理由：同一份报告放两处 = **双真源**，迟早不一致（`CONVENTIONS.md` §9 原话）。
2. ★ **历史不回填。** 目录改名 / 迁移**不改已发表记录正文里的旧路径** —— 那是**当时的事实**；
   只修**活文档**（`docs/` · `registry/`）与**真链接**。
   - 实证：本轮迁移中，`reviews/X-*.md` 内 **40 处** `records/X-…` **刻意保留**；`.workbuddy/memory/` 里 **19 处**同为历史，保留。
3. ★★ **判据要接受两种目录名。** 凡「比对**历史提交里的路径**」的判据，必须**同时接受旧名与新名**。
   - 实证：`records/` → `reviews/` 后，`check-records.js` 的 `C5` 一度把 **7 个历史提交误报**成
     「改了契约却无同批记录」—— 处置走 **「判据修正」（首选路）**：`RECORD_RE[ROOT]` 改为
     `/(?:records|reviews)\/X-\d+\.md$/`，**不是**给 7 个提交逐个留证豁免。

### 9.3 与「开发记录」的分工（防混淆）

| | 放哪 | 编号 | 是什么 |
|---|---|---|---|
| **审阅记录** | **`reviews/X-*.md`** | `X-` | **谁审谁**的过程与结论 |
| 开发记录 | `qiuyuan-dalu/records/T-*.md` | `T-` | **干活**的卡（**含「审阅响应」的追加节**） |
| 台账 | `registry/cross-repo-ledger.md` | 索引 `X-` | 一行一事，**链接指向 `reviews/`** |

★ **下游收到审阅后的「响应」不另开文档** —— 写在该卡的 `T-*` **追加节**里（如 `T-0027` §追加三）。
理由：**响应是开发动作，不是审阅文档**；另开文档会让「审阅文档」这个概念长出第二义。

## 10. 项目群全量审查（跨仓 ＋ 世界观库 · `v1.7` 新增）

> **与 §3 的关系**：§3 管「**一次审一个对象**」的动作顺序；本节管「**一次审多个对象**」时
> **对象怎么列、怎么分工、往哪落**。★ **判据 / 证据 / 二值判定 / 归类一律仍走 §2／§3／§4／§5** ——
> 本节**不另立判据**（§2 第 2 步「不自造判据」对全量审查同样生效）。

### 10.2 分工：按**对象**切，不按维度切
