## 1. 手机端用什么方案（上游已裁，本文件不重开）

### 1.1 三条路线与结论

| 路线 | 原理 | 画质 | 延迟 | 成本 | 结论 |
|---|---|---|---|---|---|
| **A 原生移动端** | UE5 Mobile 渲染管线，手机本地跑 | 中（比 PC 降一档） | 低 | 开发成本高（资产要压） | ✅ **主路线** |
| **B 云串流** | PC 渲染，手机只当视频终端 | 最高（等于 PC） | 高（依赖网络与节点） | 算力成本随在线**线性上涨** | ✅ **低端机兜底** |
| **C 混合** | 战斗/副本走原生，重场景走串流 | 高 | 视场景 | 最复杂 | ⚠️ 后期可选 |

> **为什么不选纯串流**（上游原话）：串流算力成本**随在线人数线性增长**，而 MMO 商业模式恰恰依赖**大量低付费长在线用户** —— 算不过账。
> 纯串流适合「短时高画质体验」（云游戏平台的单机大作），**不适合 MMO**。

**本项目结论：原生 UE5 Mobile 为主 + 云串流兜底低端机。** 云串流是**服务端侧**的事（渲染节点 + 推流），**不进客户端目录**。

### 1.2 三阶段推进（上游 §4.2）

| 阶段 | 手机端动作 | 成本 |
|---|---|---|
| **现在（原型期）** | 只做一件事：**定死移动端资产预算**，让 AI 生成资产时遵守 | 近零 |
| **验证期** | 用 **Mobile Preview** 定期检查场景在移动管线下是否可呈现 | 低 |
| **商业化期** | 正式做**原生移动端**（打包 Android / iOS） | 高（此时才投入） |

### 1.3 一个必须现在决定的事（上游 §0.3 原话）

> **PC 原型期若用了 Lumen / Nanite / 高面数 Nanite 资产，转移动端时资产要重做一遍。**

> ### 这是「提前准备」的真正含义
> **不是准备一个目录，是准备一套约束。**
> 让 PC 阶段产出的资产**本身就是移动端可用的** —— 否则 PC 做完才发现要重做，「提前准备」就白做了。

## 2. 做完 PC 后怎么变成安装包

### 2.1 第一件要说清的事：**不需要另做一遍**

**UE 是单工程多平台。** 同一份 `QiuyuanDalu.uproject`，**切一个 Target Platform 出不同包** ——
不存在「PC 版做完，再做一个手机版」。

```
ue-client/                                    ← 唯一的 UE 工程
   ├─ Content/  Source/  Config/              ← 双端共用（同一份资产、同一套玩法代码）
   └─ Config/{Android,IOS}/  DeviceProfile    ← 平台差异只在这里
        │
        ├─ Target: Windows → 出 PC 包
        ├─ Target: Android → 出 .apk / .aab
        └─ Target: IOS     → 出 .ipa（⚠️ 只能在 Mac 上，见 §2.4）
```

> **代价不在代码，在资产与渲染。** 逻辑层与资产**共用**；**要变的**是渲染管线特性（Lumen→烘焙、Nanite→关、BC→ASTC…）与平台预算。
> **故「提前准备」= 从第一天守资产预算**（§3.1），不是「准备两套工程」。

### 2.2 三条出包链路

| 目标 | 工具 | 关键参数 | 产物 |
|---|---|---|---|
| **Windows（PC）** | `RunUAT.bat BuildCookRun` | `-platform=Win64 -clientconfig=Shipping -cook -build -stage -package -archive` | `Windows/` 目录（`.exe` + `Paks/`）→ 再套安装器 |
| **Android** | 同上 | `-platform=Android -cookflavor=ASTC` | **`.apk`**（国内渠道）/ **`.aab`**（Google Play） |
| **iOS** | ⚠️ **只能 macOS + Xcode** | 同参数，但在 Mac 上跑 | **`.ipa`** |

**PC 的「安装包」怎么来**：UE 只出「可运行目录」（`.exe` + 资源），**安装包要再套一层**——
`Inno Setup` / `NSIS`（免费、脚本化）打成 `.exe` 安装器；或直接**走 Steam / Epic 平台**（它们自带分发）。

**命令骨架**（`<ENGINE>` = `F:/zxc/UE_5.8`）：

```bat
:: Windows Shipping 包
"%ENGINE%\Engine\Build\BatchFiles\RunUAT.bat" BuildCookRun ^
  -project="F:/zxc/Project/qiuyuan-dalu/ue-client/QiuyuanDalu.uproject" ^
  -noP4 -platform=Win64 -clientconfig=Shipping ^
  -cook -build -stage -package -archive ^
  -archivedirectory="F:/zxc/Project/qiuyuan-dalu/build/win64"

:: Android（ASTC 贴图；AAB 加 -packageforplay）
"%ENGINE%\Engine\Build\BatchFiles\RunUAT.bat" BuildCookRun ^
  -project="...QiuyuanDalu.uproject" -noP4 ^
  -platform=Android -cookflavor=ASTC -clientconfig=Shipping ^
  -cook -build -stage -package -archive -archivedirectory=".../build/android"
```

### 2.3 三条链路的前置（**实测状态**，2026-09-28）

| 链路 | 前置 | 实测 | 阻塞 M1？ |
|---|---|---|---|
| **Windows** | UE + MSVC | ⚠️ **MSVC `14.44.35207` 被 UE 5.8 禁用**（`14.44.0-14.44.35210`） | 🔴 是 |
| **Android** | Android Studio（SDK / NDK / JDK 17） | ❌ **未配**（`ANDROID_HOME` 为空） | ❌ 否（M1 不打包） |
| **iOS** | **macOS + Xcode** | ❌ **本机是 Windows，物理上不可出包** | ❌ 否 |

**Android 前置的走法**（将来做时）：
1. 装 Android Studio（含 SDK + 一个版本的 NDK）
2. 跑 `<ENGINE>/Engine/Extras/Android/SetupAndroid.bat`（NDK 默认 `27.2.12479018`，脚本会写 `ANDROID_HOME`）
3. 在 `Project Settings → Platforms → Android` 填 **包名**（`AndroidPackageName`）、**SDK 版本**、**keystore 签名**
4. 出包（§2.2）

### 2.4 iOS 的硬约束：**Windows 出不了 iOS 包**

> ### ⚠️ 这一条必须现在就知道，不能等到做的时候才发现。
> iOS 的编译与签名**依赖 Xcode**，而 Xcode **只在 macOS 上**。本机是 Windows → **物理上无法产出 `.ipa`**。

**三条应对**（择一即可，现阶段**都不必做**）：

| # | 方案 | 代价 |
|---|---|---|
| 1 | **先只上 Android** | 最低。国内渠道也以 Android 为主 |
| 2 | 买 / 租一台 **Mac**（或云 Mac）做 iOS 构建机 | 中 |
| 3 | 用 **macOS CI**（如 GitHub Actions 的 macOS runner）跑打包 | 中，需配 CI |

> **对本项目的影响**：**M1 到 M17 全程无影响**。它只影响「商业化期要不要上 iOS/App Store」这个决策 —— **现在登记，不必现在解决**。

### 2.5 云串流（B 路线）在哪一侧

云串流**不是客户端工程的事** —— 它是**服务端侧**（渲染节点集群 + 视频推流 + 输入回传）。
故：**不进 `ue-client/`，也不进 `platforms/mobile/`**，归**服务端线**（方案 §8）。本文件只登记其存在。

## 3. 「提前准备」的两件含义

### 3.1 含义一：**约束**（更要紧）

上游 §4.4 给了「双端资产预算」。**上游那张表是「移动端目标」，本项目要拍板取什么值** ——
下表的**「本项目取值」列是本仓真源**；「依据」列是上游上限，**冲突以上游为准**（ADR-0002）。

| 资产类 | 上游移动端目标 | **本项目取值** | 落地动作 |
|---|---|---|---|
| 主要角色模型 | 1.5–3 万面 | **≤ 3 万面** | GBE 生成后降面 |
| NPC / 杂兵 | 5 千–1.5 万面 | **≤ 1.5 万面** | 远景可用 impostor |
| 建筑模块（单件） | 3 千–1 万面 | **≤ 1 万面** | 模块化拼装 |
| 场景总面数（同屏） | ≤ 15–20 万面 | **≤ 20 万面** | LOD + 剔除 |
| 角色贴图 | 1024²（主角 2048²） | **1024² / 主角 2048²** | **保留无损源** |
| 材质指令数 | ≤ 30–40 | **≤ 40** | 材质作者遵守 |
| 骨骼数（角色） | ≤ 75 | **≤ 75** | **绑定前定死** |
| LOD 层级 | 3–4 级 | **4 级** | — |
| 动画帧率 | 15–20 fps | **20 fps**（可插值） | — |
| 同屏可见玩家 | ≤ 20–30 | **≤ 30**（其余降级表现） | MMO 常规做法 |

**落地方式**（上游原话）：**「宁可在产出时就压到移动端规格，也不要生成高模再回头降。」**
→ 这张表做成**资产验收清单**，AI 生成的资产**先过表再入库**（挂 `contracts/asset-ref-contract.md`）。

**唯一不可后补的两条**（`PROJECT-STRUCTURE.md` §7.2 已论证）：

1. **资产规格** —— 返工无捷径；
2. **输入抽象** —— 全走 Enhanced Input 的 `IA_*` / `IMC_*`，**玩法代码不读键码**（否则重构）。

### 3.2 含义二：**归置**（大人要的）

把手机端相关产出物**集中到一个明确的位置**，现在建、现在填真内容 —— **避免将来「找不到 / 忘了」**。
归置方案见 §4，内容清单见 §5。

## 4. 归置表：每类东西放哪

### 4.1 先否掉一个错解：**不是「第二个 UE 工程」**

> ❌ **不建** `ue-client-mobile/`。
> 两个 UE 工程 = **资产维护两套 = 双真源** —— 直接违反 ADR-0002 精神，
> 并违反上游 §4.5「**同一套玩法逻辑，双端共用**」。

**正确形态**：**单工程多平台**（§2.1）；「手机端目录」装的是**工程外**的平台专属产出物。

### 4.2 归置表（**核心**）

| 东西 | 放哪 | 为什么放这 | 何时落 |
|---|---|---|---|
| **资产预算 / 验收清单** | `platforms/mobile/asset-acceptance.md` | 是**平台专属门槛**，不是通用规范 | M1（建目录时即落，§5） |
| **出包脚本（Android / iOS）** | `platforms/mobile/build/` | 按**域**组织（同 `Content/` 按功能，不按类型） | M1 落占位，出包时填 |
| **签名 / 证书配置模板** | `platforms/mobile/signing/` | ★ **真实密钥不入库**，只入库**模板与说明** | 出包前 |
| **机型分级表** | `platforms/mobile/device-tiers.md` | 低 / 中 / 高 / 旗舰 —— 与 DeviceProfile 一一对应 | 验证期 |
| **迁移工单（PC→移动端）** | `platforms/mobile/render-migration.md` | 上游 §4.3 十项的**本项目逐项打勾表** | 验证期 |
| **平台配置（ini）** | ★ **`ue-client/Config/Android/` `Config/IOS/`** | **UE 规定的位置**，挪出去引擎不认 | 按需建，不预建 |
| **设备分级（DeviceProfile）** | ★ **`ue-client/Config/DefaultDeviceProfiles.ini`** | 同上 | 验证期 |
| **平台专属 UI 布局** | `ue-client/Content/QiuyuanDalu/UI/` 内按平台分 | 资产必须**在工程内** | 商业化期 |
| **云串流** | ✗ 都不进 | **是服务端侧的事**（§2.5） | — |

> **★ 两条口诀**：
> **① 引擎认位置的东西（`Config/<Platform>/`、`Content/`、DeviceProfile）→ 必须在 `ue-client/` 内，别想挪。**
> **② 引擎不认的东西（脚本、清单、签名模板、机型表）→ 归 `platforms/<平台>/`，按域组织。**

### 4.3 `platforms/` 为什么不并进 `tools/`

方案 §1 已有 `tools/`（校验 / 构建脚本）。**仍单开 `platforms/`**，理由：

| | `tools/` | `platforms/` |
|---|---|---|
| 组织维度 | 按**类型**（都是脚本） | 按**域**（都是「某个平台专属的东西」） |
| 内容 | 跨平台**通用**工具（校验、生成） | **平台专属**（签名、商店资料、机型表、出包） |
| 判断 | 一份脚本双端都用 → `tools/` | 只有手机端用 → `platforms/mobile/` |

> 与 §4 Content「**按功能不按类型**」同一条原则。**且将来加主机（PS / Xbox / macOS）时，是平级新增 `platforms/<新平台>/`，不动现有结构。**

### 4.4 `qiuyuan-dalu` 目录增量

在 `PROJECT-STRUCTURE.md` §1 的目录树中**新增一级**：

```
qiuyuan-dalu/
├─ ue-client/          ★ UE 工程（单工程 · 多平台）
├─ platforms/          ★ 平台专属产出物（工程外）
│  └─ mobile/          手机端（M1 建目录 + 落 §5 清单）
├─ server/   data/   admin/   db/   tools/
└─ docs/  tasks/  records/  tests/
```

**M1 只建 `platforms/mobile/` 并落 §5 的文件** —— 不是空目录（有真内容），不违反「不留空壳」纪律（方案 §3.2）。
**`platforms/` 下不建** `desktop/` —— **PC 就是默认路径，不需要专属目录**（只在 `platforms/mobile/` 有东西可放）。**不留同构空目录。**

## 6. 启停判据：**什么时候开始做手机端**

**现在不做的判据**（沿用 `PROJECT-STRUCTURE.md` §7.1）：

> **一个决定，如果「不做」会在将来做移动端时推翻已写的东西 → 现在做。**
> **「不做」将来只是补一个配置 / 一套布局 → 现在不做。**

| 项 | 现在 | 何时做 | 触发条件 |
|---|---|---|---|
| 资产预算约束 | ✅ **做** | — | M4 起每个资产入库过表 |
| 输入抽象（Enhanced Input） | ✅ **做** | — | M1 起代码纪律 |
| 保留无损源 | ✅ **做** | — | 资产生成即执行 |
| **Mobile Preview 检查** | ❌ | **验证期** | 场景可玩后，**每个大版本末跑一次** |
| DeviceProfile / 机型分级 | ❌ | 验证期 | 有真机数据后 |
| ASTC 贴图批量转 | ❌ | **出包时** | 打包流水线里自动做 |
| Android 出包链路 | ❌ | 商业化期 | 决定上安卓时 |
| iOS 出包链路 | ❌ | 商业化期 | ★ **先解决「有没有 Mac」**（§2.4） |
| 竖屏 UI 布局 | ❌ | 商业化期 | 上游 `UI与界面设计.md` 已有区分 |

**唯一「现在必须做」的三项全是纪律/约束，不是投入** —— 一次点击或一条规矩，代价近零，**事后不可补**。
