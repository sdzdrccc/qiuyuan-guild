## 0.0 第一设计原则 —— **世界真实性优先**

> **效力**：本节是**第一原则**，**高于本方案全部章节**，也高于 `docs/DECISIONS.md` 的其余 ADR。
> 其余任何裁决若与本节冲突，**以本节的判据重新裁决**。
> 来源：**大人裁决**（2026-09-28）+ 上游依据（`10-MMO化/MMO化总览.md` §核心设计原则「真实修真体验」）。详见 **ADR-0009**。

### 原则

> **尽量还原真实修真的世界，力求身临其境 —— 不是单纯为了做游戏而实现功能。**

上游已经写过「真实修真体验」，但它**列在四条并列之中**，且只说「还原哪些系统」（灵根 / 体质 / 境界 / 天劫）。
本节做两件事：**① 提为第一原则；② 补上「怎么判断一个设计是否忠于世界」的判据** —— 这是上游没给的。

### 「真实」≠ 物理拟真

**「真实」= 内部一致 + 因果闭环 + 规则不迁就玩家。**

| 维度 | 含义 | 反例 |
|---|---|---|
| **付出有代价** | 一切收益都有对应风险 / 消耗 | 突破必成功、死亡无损失 |
| **实力有依据** | 强弱可追溯到来源（境界 / 灵根 / 法宝 / 功法） | 靠充值或运气凭空变强 |
| **规则不为玩家转弯** | 世界按自己的逻辑运行，玩家只是其中一员 | 高阶修士为等玩家而放水；秘境按玩家等级调难度 |
| **因果可见** | 玩家能理解「为什么发生」 | 数值黑箱，结果无解释 |

> **判据（一句话）**：**玩家感到「这是一个会自己运转的世界，我只是恰好在这里」，而不是「这是一台为我服务的机器」。**

### 三问（新系统 / 新玩法 / 新功能开工前必答）

| # | 问题 | 不合格的判据 |
|---|---|---|
| **1 世界依据** | 这件事在世界观里**如何存在**？出处在哪一页？ | 答不出 → **先开上游任务卡，或砍掉**。**不得凭「别的游戏都这么做」立项** |
| **2 感知路径** | 玩家怎么**感觉到**它？ | 只能通过**面板数字**感知 → 不合格。数值可以是结果，不该是唯一的体验面 |
| **3 删除测试** | 删掉它，玩家失去**一段体验**还是**一个功能**？ | 答「一个功能」→ 它是**为做功能而做**的 |

### 冲突裁定

**世界逻辑 × 玩法便利 冲突 → 世界逻辑优先；玩法在世界的框架内找解法。** 但须区分：

| | 定义 | 可否牺牲 |
|---|---|---|
| **可玩性** | 能完成目标、不卡死、不因纯随机彻底白费投入 | ❌ **不可牺牲**（本原则的底线） |
| **便利性** | 一键传送、自动寻路、数值直给、弹窗指路 | ✅ **可牺牲**（换成世界内的手段） |

> **例**：目标是「让玩家知道该去哪」。❌ 弹箭头指路 ｜ ✅ 宗门执事口述、舆图卷轴、神识标记。
> **目标不变，手段换成世界内的。**

### 边界（防止被滥用）

本原则**不是**「越硬核越好」（**难不是目的，真实感才是**），**不是**「拒绝一切游戏化手段」（手段可用，须过三问），**不是**「照搬小说的每一条」（小说里没有「操作」，把设定翻译为可交互系统本身就是创作）。

### 落地（**不可自动校验 → 人工检查点**）

三问的答案都是**语义判断**，脚本只能查「有没有填出处」这种**形式**，反而会催生**填假出处**（与 §7.1 纪律 1「虚假的安心」同类）。

**故按 §7.1 纪律 5 处置：**

| 项 | 落地 |
|---|---|
| **任务卡** | 新增必填栏「**世界依据**」—— 策划类任务**缺此栏即不合格** |
| **审核** | 审核清单固定加两项：**感知路径** / **删除测试** —— **二值判定**，不得评分（§5.5） |
| **范围** | **新系统 / 新玩法 / 新功能**；纯重构 / 修 bug / 排版类**不适用** |
| **登记** | `CONVENTIONS.md` **§7.4 人工检查点登记** 第 1 号 |

> **为什么不写成脚本**：把「能机械校验的」与「只能人判的」分开 —— **锚点存在性**可自动查（`check-data.js` 新增 **R9**）；**三问答案对不对**只能人判。**拿脚本假装能判后者，就是虚假的安心。**

> 契约若住进 **`qiuyuan-dalu`** → 原型把已验证结论回流契约，就等于「写 dalu」，**第二条铁律当场破掉**。
> 所以只要**同时存在两个执行方**，契约就必须住在第三方。

**但这个独立有保质期**：

> **Phase 4 原型退役后，只剩 `qiuyuan-dalu` 一个执行方**——届时契约层可降格为 `dalu/contracts/` + `dalu/docs/`，**独立仓即可取消**。

**它是「预留的格子」，不是空壳。** Phase 0 一次补齐。
> **v0.14 更新**：Phase 0 已补齐，且 v0.14 又新增 `DECISIONS.md`（ADR 台账）与 `ROADMAP.md`（里程碑路线图）—— 见 §3.1 目录。

### 2.1 纵向：4 个模块 owner（对齐 14 个官方模块）

| Agent | 覆盖官方模块 | 职责 | 独占领地（**模块子树 · 跨端**） |
|---|---|---|---|
| **`world`** | A 账号角色 · B 成长境界 · D 技能功法 · E 装备法器 · F 物品经济 · G 生活职业 · J 社交宗门 · K 灵兽 · M 任务剧情（数据侧） | **数据层**：全部数值与配置表 + 对应服务 | `data/` · `server/internal/world/` · `ue-client/…/World/` |
| **`combat`** | C 战斗（12 项） · H PVE · I PVP · D/K 的逻辑侧 | 战斗结算、技能释放、AI、掉落 | `server/internal/combat/` · `ue-client/…/Combat/` |
| **`scene`** | L 开放世界（9 项） · H/M 的场景侧 · G 的场景侧 | 地图、场景、据点、副本场景 | `server/internal/scene/` · `ue-client/Content/Maps/` |
| **`ui`** | N UI 与运营技术 · A 角色创建界面 · J 界面 · E/F 界面 | HUD、功能页、交互 | `ue-client/Content/UI/` |

> **「独占领地」是模块子树，不是顶层目录**（v0.11 修订）——这是**服务端重写 Go 带来的必要修正**：
> `server/` 与 `ue-client/Source/` 都会被多个 owner 写，写权边界**必须下沉到模块子树**（Go 用 `internal/<module>/`，UE 用 `Source/<Module>/`）。
> **判据不变：一列一主，同一时刻同一个子树只有一个 agent 有写权。**
> 上表的具体路径待 **M1** 骨架建立时落实（`world` 的 `data/` 已确定在 repo 根，见 §3.2）。
>
> **v0.24 补注（ADR-0016）—— Go 侧路径已落实**：上表 `server/internal/world/` 等写法是 **v0.11 的示意**。`server/` 结构已裁定为「**技术模块切**」→ Go 侧**一级目录 = 进程名**（`gateway/` `login/` `game/` `platform/`），**owner 写权改以子树内声明（`OWNERS`）表达**，不再用 `internal/<owner>/` 做一级目录。
> **本表 owner 体系不变**（4 owner + 14 模块覆盖度不动），变的只是「模块子树」在 **Go 端**的形制。详见 `docs/SERVER-ARCH.md` §6（**ADR-0016**）。

**映射原则**：一个官方模块**可以跨两个 agent**，但必须分清「数据归 `world`、逻辑归 `combat`/`scene`/`ui`」。以模块 D（技能功法）为例——技能数值表归 `world`，技能释放与冷却归 `combat`。

**覆盖度自查**（84 项全部有主）：

| Agent | 主导项数 | 说明 |
|---|---|---|
| `world` | ~62 | 数值与配置表是最大头，也是迁移期最该重投的 |
| `combat` | ~28 | C/H/I 三个模块 + D/K 逻辑 |
| `scene` | ~15 | L 全模块 + H/M/G 场景侧 |
| `ui` | ~20 | N 全模块 + 各处界面 |
| **合计** | **84+**（含跨主项） | 无遗漏 |

> ⚠️ **负载不均是本方案最大的结构性风险**：`world` 覆盖 **9 / 14** 个模块（A/B/D/E/F/G/J/K/M），主导约 62 项。
>
> **为什么不能简单拆**：`world` 管的是**同一份数据的完整性**——境界属性、技能表、物品表之间互相引用，若拆给两个 agent 并行写，「写权唯一」这条铁律会被破掉，结果比不拆更糟。
>
> **缓解办法**（按优先级）：
> 1. **按批次推进，不并行**——`world` 是瓶颈就让它单线跑，其他 agent 等它的契约交付。
> 2. **任务卡带模块标签**，让 `world` 的工作可排队、可显式调度（但同一时刻仍只有一个 `world` 在写）。
> 3. **若确需拆分**，正确的切法是按**数据簇**而非按模块：`world-data`（境界/属性/技能——成长主干）＋ `world-item`（物品/经济/装备——经济侧）。两簇之间引用关系最弱。
>    **但先别拆**——等 **M1** 跑完、看到真实瓶颈再决定。过早优化会白花协调成本。

> **⚠️ 与里程碑制的关系（v0.14 补注）**：上面的分工表是**「谁管什么」**（覆盖度），**不等于「什么时候做」**。
> **执行顺序按 `docs/ROADMAP.md` 的里程碑走** —— 一个里程碑只涉及表中少数几行。
> 例如 **M1 只用到 `world`（数据侧）+ `ui`（三个界面）**，`combat` / `scene` **在 M1 不参与**。

### 2.2 外部：1 条资产线（不是本项目内的 agent）

`asset` **不在本项目内**——它是 gbe-studio 的职责。

本项目的角色是**资产消费者**：
- 读 `gbe-assets/kits/` 的构件与 `assemblies/` 的装配清单
- 校验交付包是否符合本项目的**引用契约**（命名、尺寸、锚点、LOD）
- **不符合就退单**，不退而求其次自己改

### 2.3 横向：4 个职能 agent（只读 + 产出审计物）

| Agent | 职责 | 产出物 | 写权边界 |
|---|---|---|---|
| `arch` | 守契约、裁决接口与数据变更 | ADR、契约文件 | **唯一有权改契约** |
| `review` | 按产物类型执行审核 | 审核报告 | 只读 |
| `qa` | 写/跑测试、跑门禁 | 测试用例、测试报告 | 只写 `tests/` |
| `ledger` | 汇总完成记录、查账、发版 | `DEVLOG.md`、CHANGELOG | 只写记录类文件 |

### 2.4 矩阵

```
              world   combat   scene    ui     [asset 外部]
  arch          ├────────┼────────┼───────┼──────┤   守契约（横切）
  review        ├────────┼────────┼───────┼──────┤   审计（横切）
  qa            ├────────┼────────┼───────┼──────┤   测试（横切）
  ledger        ├────────┼────────┼───────┼──────┤   台账（横切）
                └── 每列写权唯一，每行只读横切 ──┘
```

**一条硬规则**：横向 agent 永不直接改纵向模块的业务文件。发现问题 → 开任务卡 → 交回 owner。这条一破例，写权就失效了。

**为什么不是「一模块一 agent（14 个）」**：单人项目下，14 个 agent 的协调与上下文成本会超过产出。4 个纵向 owner 让「写权唯一」这条规则可执行；模块的细分靠**任务卡上的模块标签**表达，不靠 agent 数量。

## 4. 文档规范：契约先行

### 4.1 顺序不可颠倒

```
改契约（arch 裁决，落 ADR）
   → 改数据/实现（模块 owner）
   → 改测试（qa）
   → 记录（ledger）
```

**反模式**：先写代码或先填表，回头「补一下契约」。契约会退化成文档，失去约束力。

### 4.2 铁律（沿用 GBE 已验证的体例）

1. **契约是唯一真源**，代码与数据服从契约，不是反过来。
2. **ADR 只追加**——推翻旧裁决 = 新增一条带 `supersedes: ADR-xxxx` 的 ADR，**历史条目一个字都不许改**。（`gbe-assets/docs/DECISIONS.md` 已是这个体例）
3. **枚举必须留 `unknown`**。凡要向后回填的枚举，必须允许「未核实」取值，否则回填时只能二选一，标哪个都是撒谎。
4. **有分歧先查上游**：先查 `gbe-assets/docs/DECISIONS.md` → 再查 `虬渊大陆` 对应页 → 都没有才问大人，答复后**落一条 ADR 再动手**。（与 gbe-studio/AGENTS.md §5 一致）

### 4.3 契约校验要能自动跑

```bash
node scripts/check-data.js        # 配置表 ↔ data-contract.md 一致性
node scripts/check-asset-ref.js   # 场景引用 ↔ 资源清单 ↔ 实际资产
node scripts/check-interfaces.js  # 跨模块接口 ↔ interfaces.md
```

**没有校验脚本的契约 = 装饰品。**

### 4.4 三处 schema 的层次（v0.11 新增 · 裁决 14）

生态里现存**两处** schema，加上 guild 计划中的 `contracts/`——**是三层，不是三个真源**。层次不写清，「契约唯一真源」这句话就会落空（迟早出现同名不同义的 schema）。

| 层 | 位置 | 管什么 | 产生方 | 消费方 | 变更节奏 |
|---|---|---|---|---|---|
| **L1 管线内部** | `gbe-studio/core/contracts/` | 生成管线内部数据结构：`generation-job` / `generation-artifact` / `ledger-entry` / `refine-recipe` / `decomposition-plan` / `engine-import-plan`（6 个） | gbe-studio | gbe-studio 内部 | 随流水线版本走 |
| **L2 资产包交付** | `gbe-assets/packages/schema/` | 资产**交付包**的契约：`assembly` / `validate` / `index` | gbe-assets | 游戏侧（dalu）、原型 | 随资产包格式走，**改需 ADR** |
| **L3 游戏侧** | `qiuyuan-guild/contracts/` | **游戏消费面**契约：数据模型 / 资产引用 / 协议 / 资源清单 | guild | dalu、原型 | 随游戏需求走，**改需 ADR** |

**层次规则（三条 · 硬性）**：

1. **不跨层引用。** L3 不直接引用 L1 的 schema——L3 只认 L2（资产包交付面）。**L1 怎么变，是 gbe-studio 的家事**，不外溢。
2. **同层内唯一真源。** 任一层内 schema 只有一份，其余全是消费。
3. **跨层变更必须显式。** 某层改动若影响下层（例：L2 字段改名 → 影响 L3 的资产引用契约），**须开跨库台账条目 + 在 `registry/schema-layers.md` 登记**。

> **登记表**：`guild/registry/schema-layers.md` 是这三层的**索引**（每层一行：位置 / 版本 / 负责方 / 最近变更），**不是 schema 副本**。它存在的唯一目的——让「层」这件事**在物理上可见**。

## 5. 审核机制：消费者审核 + 分级触发

### 5.1 核心问题：agent 审 agent 会互相放水

同一模型、同样盲区，A 写 B 审，B 大概率看不出 A 的错——**不是态度问题，是能力同构**。

### 5.2 破解：审核者必须是「下游消费者」

不是随便找另一个 agent，而是让**真正要消费这份产物的人**来审：

| 产物 | 审核者 | 判据 |
|---|---|---|
| `world` 的配置表 | `combat` + `ui` | 它们要读这份数据，读不通立刻暴露 |
| `combat` 的接口 | `ui` | UI 要调它 |
| `scene` 的场景 | `asset`（尺寸/锚点）+ `qa` | 资产要装进场景 |
| `ui` 的界面 | `world` | 需要的数据字段是否存在 |

**「这个字段我读不到」比「这个设计不好」有力一万倍。**

### 5.3 审核分级（按变更影响面触发，不搞全量多审）

| 级别 | 触发条件 | 审核者 | 强度 |
|---|---|---|---|
| **L0 自检** | 所有任务，必做 | 作者 + 校验脚本 | 机器可验 |
| **L1 消费者审** | 改动跨出模块边界 | 1 个下游 owner | 必做 |
| **L2 会审** | 影响 ≥2 模块，或动资产汇合点 | 2–3 个 owner + `qa` | 按需 |
| **L3 终审** | 改契约 / 改架构 / 发版 | `arch` + 大人 | 不可省 |

**判据只有一句**：「这个改动，会不会让别人手里的东西失效？」——会，就至少 L1。

### 5.4 审核清单必须可证伪

```markdown
## L1 消费者审核清单（combat 审 world 的境界属性表）

- [ ] 每个境界的 15 项属性在表中都有列（实测：9 境 × 15 项 = 135 格，缺 0）
- [ ] 属性值与 [[境界基础属性]] 逐行一致（抽查 3 行，附对比）
- [ ] 字段类型与 data-contract.md 声明一致
- [ ] 枚举列无空值（未核实项须显式写 `unknown`，实测：0 处空值）
```

### 5.5 判据形态：**二值判定** + **四个客观计数**（v0.15 新增 · ADR-0008）

**审核结论只有二值**：`通过` / `不通过`（+ 未通过项**逐条列出**）。**不得出现分数、等级、满意度百分比。**

**禁止「其他 agent 给产出打分」。** 三条理由：

1. **与 §5.1 正面冲突** —— 同构互审会放水，而**分数比二值更容易放水**：连续量可以「给个面子 8 分」，二值量**没有中间地带**。
2. **Goodhart 定律** —— 分数一进记录，agent 即为**分数**优化：把任务切碎（个个高分）、把范围写模糊（不易被扣分）。
3. **二值清单是评分的升级版** —— 「9 境 × 15 项 = 135 格，缺 0」没有中间地带。**评分制是审核的降级。**

> **最根本的一条**：四个纵向 agent 是**同一个模型扮的四个马甲**（§5.1 的前提即「能力同构」）。
> **给马甲排名 = 给同一个模型的四次发言排名。** 无信息量，且会引发为排名优化。

**需要量化时，只量化「客观事件计数」**（由 `ledger` 从 `records` 统计，**不新增填报字段**）：

| 计数 | 定义 | 红了说明什么 |
|---|---|---|
| **返工次数** | 同一张任务卡被退回的次数 | 任务卡写不清 / 交接判据缺失 |
| **门禁失败次数** | `check-*.js` 红了几轮 | 契约与产物脱节 |
| **契约变更次数** | 本里程碑改了几次 `contracts/` | **契约没想清就开工** |
| **遗留转出数** | 本卡抛给下一张卡的 TODO 数 | 范围闸门没关严 |

> **这四项是「事实」，不是「打分」**，且**不可被优化** —— 想降低返工次数，**唯一办法是别返工**。
> 四项指向**流程环节**，**不指向执行者**。**禁止据此评价 agent 或个人。**

## 6. 记录机制：强制产出 + 台账查账

> **⚠️ v0.12 界定范围**：本机制在**两处**生效，按任务**发起方**切分（推导见 §0 修正五 5.4）。
>
> | 发起方 | 落点 | 记什么 |
> |---|---|---|
> | dalu | `dalu/tasks/` `dalu/records/` | 本工程实现任务（写代码 / 做场景 / 配表） |
> | **guild** | **`guild/tasks/` `guild/records/`** | **跨库任务 + 契约 / 纪律 / 准入变更** |
>
> **硬判据**：**`records` 必须与它描述的改动同仓**——否则 6.2 的第一条交叉查账（「记录里的改动清单与 git diff 一致吗」）**跨仓失效**。
>
> 这一条把「契约层不可追责」的缺口堵上：`guild/contracts/` 是唯一真源且会被改，每次改动也是一次任务，同样要产记录。
>
> 上游库内部任务 → 写在上游**自己的**记录体系里，guild 只持**指针 + 验收结论**（不代写、不复制）。
>
> **编号前缀区分（避免两仓同号）**：两处 `records/` 若都用 `T-<编号>`，dalu 的 `T-0012` 与 guild 的 `T-0012` 会撞，引用时无法分辨。
> 故：**dalu 用 `T-<编号>`**（task）；**guild 用 `X-<编号>`**（cross-repo）。
> `registry/cross-repo-ledger.md` 的每一行引用的是 `X-*`；`§6.1` 的记录模板对两处通用，仅编号前缀不同。

### 6.1 每个任务必须产出完成记录

`records/T-<编号>.md`：

```markdown
# T-0012 境界属性配置表（B 成长与境界）

- 状态：已完成 / 部分完成 / 阻塞
- 执行者：world
- 覆盖官方模块：B 成长与境界（MMO功能清单 7 项）
- 加载的 skill：luban-table-gen（自建）
- 契约引用：data-contract.md §2.1 / 上游 10-MMO化/境界基础属性.md

## 改动清单
- 新增 tables/realm_attribute.xlsx（15 项属性 × 9 境）
- 修改 contracts/data-contract.md §2.1（新增 layer 字段）

## 验证证据（必须可复现）
$ node scripts/check-data.js
→ 135/135 通过

## 审核
- L1 审核者：combat
- 结论：通过
- 未通过项：无

## 遗留问题
- 灵兽出战仇恨字段未定 → 转 T-0018

## 执行环境（可选 · 仅供回溯）
- 工具 / 版本：<如 WorkBuddy 1.x>
- 模型：<如 claude-sonnet-4.5>
- 日期：<YYYY-MM-DD>
```

**「验证证据」必须是命令 + 实际输出**，不是「已测试通过」。无可复现证据的记录，台账直接驳回。

> **「执行环境」节的性质（v0.15 · ADR-0007）**：它是**指纹**，不是**评价**。
> **不参与审核、不作为质量判据、不进任何统计**；**缺失不构成**记录不合格。
> **禁止**据此排序 / 评级 / 比较 agent 或模型。
> 想比较模型优劣 → 走**独立 A/B 实验**（同一张卡双跑），**不在日常记录里做** —— 任务难度不可比，聚合出来是噪声。

**「哪个 agent 做的」由头部「执行者」字段承担**；按 agent 查全景走**派生视图** `registry/agent-log.md`。
> **它是视图，不是第二真源** —— 由 `records` 派生，可随时重生成。**视图可丢，`records` 不可丢。**

**「审核」节的判据形态见 §5.5**：只有 `通过 / 不通过`，**不得填分数**。

### 6.2 `ledger` 做交叉查账

**查账范围 = 两处 records**（`dalu/records/` 与 `guild/records/`），各与**同仓**的 git diff 对照。

- 记录里的「改动清单」与**同仓** git diff 一致吗？
- 声称的验证命令，实际跑一遍还通过吗？
- 记录说「已完成」，**同仓** `tasks/done/` 里真有这张卡吗？
- **同一契约被两个任务以矛盾方式改过吗？**（契约在 guild，故查 `guild/records/`）
- **索引与正文对得上吗？** —— `registry/cross-repo-ledger.md` 里每一条跨库需求，是否都有对应的 `guild/records/X-*.md`？反过来，有无「有正文无索引」的孤儿记录？
- **上游同步了吗？**（设计改了，配置表跟了没有）

**另统计四个客观计数**（v0.15 · ADR-0008）—— **从 records 直接数，不新增字段**：

| 计数 | 来源 |
|---|---|
| 返工次数 | 同一卡被退回的记录条数 |
| 门禁失败次数 | 验证证据里 `check-*.js` 失败的轮次 |
| 契约变更次数 | 本里程碑内 `guild/records/X-*` 涉及 `contracts/` 的条数 |
| 遗留转出数 | 各卡「遗留问题」节指向后续卡的总条数 |

> **四项是健康度指标，不是评分。** 只指向**流程环节**，**不指向执行者**。**禁止据此排名 agent。**

**对不上就退回。** 这是整套机制可信度的来源。

## 8. 引擎迁移预留（本版升级为「现在时」· 最关键）

「先 Godot 后 UE5」不是一句口号，而是**此刻就约束投入的准则**。它推出五条可执行纪律。

### 8.0 原型只做验证（v0.7 新增 · 第零条）

**原型的每一行代码都是消耗品，原型唯一的产出是「已验证的结论」。**

| 该做 | 不该做 |
|---|---|
| 验证玩法闭环是否成立 | 优化原型性能 |
| 校准数值手感与节奏 | 打磨原型的渲染 / 材质 / 特效 |
| 产出配置表、协议、数值表 | 在原型里堆新功能（原型的 P3~P5 不再推进） |
| 把结论提炼进契约层 | 让 UE5 侧直接读原型文件 |

**判据**：一个改动如果「迁到 UE5 时会被丢掉」，就不该做。

### 8.1 数据与逻辑彻底分离

**所有数值进配置表，代码里不出现任何硬编码数值。**

判据：

```bash
# 反例检测：脚本里不该有裸数值常量
grep -rnE "=\s*[0-9]+\s*;" scripts/ --include=*.cs | grep -v "// data-ref"
```

**为什么**：迁移 UE5 时，数据层零成本保留，逻辑层必然重写。数据与逻辑缠在一起，迁移成本会翻倍。

**原型已验证的事实**：其境界层次配置（原型名 `xx_realm_level_config`）由服务端 `RealmAttrCatalog` **公式生成**、单测对照文档数值表 —— **这条路子是对的**（公式化生成 + 单测校验），值得继承。

> **但 v0.14 有三点更正**：
> ① **「42 阶段」不是定论** —— 需求层是 **9 层 / 82 台阶**，见 `DECISIONS.md` **ADR-0004**；
> ② **「直接提炼成契约」措辞不准** —— 按 **ADR-0002**，契约的**对齐目标是需求层**，原型只是参考实作。原型的表结构**不构成权威**；
> ③ **表名 `xx_` 不入契约** —— 见 **ADR-0001**。
> **继承的是「方法与公式」，不是「表结构」。**

**✅ 配置表工具已定（v0.11 · 裁决 2）**：

| 侧 | 工具 | 理由 |
|---|---|---|
| **正式工程（UE5）** | **Luban** | 世界观库 §6.2 推荐，UE5 / C++ 语境的主流方案；schema 强约束、多语言导出、增量生成 |
| **原型（继续开发）** | **JSON** | 原型是验证器，不值得为它上 Luban 全套；原型已验证 `items.json` + DB 权威这条路可行 |

**关键一点：契约定义的是「数据模型」，不是「文件格式」。**

- `contracts/data-contract.md` 定义**字段、类型、约束、语义**——这才是唯一真源。
- 原型用 JSON、正式工程用 Luban 表——**是同一份契约的两种编码**，不是两份契约。
- **判据**：原型 JSON 与 Luban 表应能**无损互转**（写个转换脚本即可验证）。转不了，说明契约漏了字段。

### 8.2 资产保留无损源 + 中间格式

- GBE 的交付基准已是 **`+Y up / -Z forward / 米`**，up 轴由引擎导入器负责——**这个设计天生支持双引擎**（见 `gbe-studio/AGENTS.md` §2.5）。
- 本项目要做的：**消费时不落引擎特有格式**。原型期不要生成 Only-Godot 的材质 / 资源文件。
- **保留原始高精度贴图**（世界观库 §4.3 指出：BC vs ASTC 压缩格式不同，转移动端要重新生成整套贴图）。

> **⚠️ 已有反例**：原型 `.gitignore` 把 `mszl_world.glb`(42MB)、`male.glb`/`female.glb` 排除在版本控制外，
> 且这些源文件**只有一份本地副本** —— 直接违反本条。已登记为风险（§0 修正四），待大人处置。

### 8.3 场景结构按数据描述，不按引擎节点

场景的**布局数据**（哪里放什么、坐标、朝向）写进 `resource-manifest.yaml`，引擎的 `.tscn` / `.umap` 只是它的**渲染产物**。

**判据**：删掉所有场景文件能从 manifest 重新生成 → 合格。做不到，说明布局知识被埋进引擎文件了。

> 原型现状：布局知识埋在 `ProtoSpawnCity.tscn` 与 `Main.cs` 里 → **提炼时须抽出成 manifest**。

### 8.4 战斗只做「能验证玩法」的最简版

既然 GAS 会全面替换：
- ✅ 要做：伤害公式、属性生克、冷却、命中判定的**可验证实现**
- ❌ 不做：性能优化、网络预测、复杂的打断优先级

> 原型已完成的部分（物理/法术分流、生克、会心/格挡/命中、AOE）**已经验证到了位**，
> 价值在于**其数值与公式**，不在于其 C# 实现。提炼公式，丢弃代码。

### 8.5 服务端归属——✅ 已定：重写 Go（v0.11）

**裁决**：正式工程服务端**重写 Go**，对齐世界观库《技术架构与技术选型》定稿（Go 网关业务服 + UE Dedicated Server 场景服）。
原型那套 Java 21 服务端（22 个领域服务、23 张表）**降为验证器**，与 Godot 客户端同类。

> **补录（2026-09-28 · v0.23）**：本裁决发生于 **v0.11**，**早于 ADR 机制实例化（v0.14）**，故长期未进台账
> → 已**追溯补录为 `ADR-0015`**（本 ADR 只补台账，不改任何技术结论）。
> 同时登记一处**已被本裁决否决的历史方案**：2026-09-14 会话产出的 Java 单体版（主张「保留模块化单体、不微服务化、UE DS 后置」），
> 该文档**未标废弃、未登记**，且自用 `ADR-01~06` 编号与现行 `ADR-000x` 撞车 → 判为**真源污染风险**，详见 **ADR-0015 §附带发现**。
>
> **服务端进程形态与拆分时机**（九类进程 / 起步 8 合 1 / 四条拆分前提 / 何时拆 / 分线扩容）→ **`docs/SERVER-ARCH.md`**。

**由此推出两条纪律**（与 §8.0「原型只做验证」同源）：

1. **Java 侧到此为止。** 原型服务端只做「验证业务闭环 + 沉淀协议与数据表」，**不再横向扩服务**。
2. **服务端最有价值的产出是「协议 + 数据表」，不是那 22 个服务类。** Go 重写时：
   - **复用** —— `MessageTypes` 协议定义、23 张表结构、14 个迁移 SQL、数值公式
   - **丢弃** —— Spring Boot 装配、JPA 实体、22 个服务实现；**Go 侧重新实现，不逐行翻译**

> **判据**：Java 侧的某个改动，若对「协议或数据表的正确性」无贡献，就不该做——**它迁不到 Go 侧**。
>
> **⚠️ 工作量提醒**：Java → Go 是**语言级重写**，不是框架替换。22 个领域服务的重写量**不可低估**——列入跨库台账，与 UE5 骨架同批启动、**按 `ROADMAP.md` 逐个里程碑推进**（M1 只重写**账号 + 角色**两个服务）。

| 能力 | WorkBuddy | Codex | Qoder |
|---|---|---|---|
| 项目指导 | identity 文件注入 | `AGENTS.md` **层级加载**（root→leaf，最近优先） | `AGENTS.md` 静态记忆 + `.qoder/rules/**/*.md` |
| 技能 | Skill 工具，**自动加载** | `SKILL.md`，**与 WorkBuddy 同格式** | `.qoder/rules` 四种生效方式 |
| 子代理 | subagent 工具 | subagent + TOML 定制，**可设 `sandbox_mode = "read-only"`** | Quest 并行执行 |
| 记忆 | `.workbuddy/memory` | Memories | Auto-Memory |

> **来源**：OpenAI Codex 官方 Customization / Subagents 文档；Qoder 官方 Memory 文档（2026-09-27 检索留证）。

### 11.3 三条迁移纪律（重要）

1. **`AGENTS.md` 是全工具唯一锚点。** 工具私有 memory 只当缓存，**不当真源**——否则三工具混用会各自积累、互不可见，真源立刻分裂。
2. **跨会话知识一律入 git**（`docs/` + `records/`），不进任何工具的私有内存。这是「交付即产记录」的深层理由。
3. **契约层物理归 guild**，三个工具都指向同一路径。工具可换，契约不动。

### 11.4 落到具体工具的三个红利

- **Codex 能直接实现「横向只读」铁律**：`~/.codex/agents/*.toml` 给 review / qa agent 设 `sandbox_mode = "read-only"`——这不是约定，是**沙箱强制**，比口头纪律硬。
- **Qoder 的 `Always Apply` / `Specific Files` 正好对应两级规则**：铁律用 Always Apply，`contracts/**` 用 Specific Files 挂审核要求。
- **L2 自建 skill 零改写复用**：WorkBuddy 与 Codex 共用 `SKILL.md` 格式，屋顶提示词系列等 L2 资产可直接拿去。

### 11.5 规则文件的统一与分发（N 个工具）

工具越多，越不能维护 N 份漂移的规则文件。**真源只有 `AGENTS.md` 一份**，各工具按需桥接：

| 工具 | 原生文件 | 原生读 `AGENTS.md` |
|---|---|---|
| Codex / Cursor / Copilot / Gemini CLI / Windsurf / Cline / Zed / Aider | 各自原生文件 | ✅ 原生读 |
| **Claude Code** | `CLAUDE.md` | ❌ **唯一不读的**（issue 仍未合并） |
| Cursor（进阶） | `.cursor/rules/*.mdc` | ✅ 另有 glob 作用域能力 |
| GitHub Copilot | `.github/copilot-instructions.md` | ✅ |
| Gemini CLI | `GEMINI.md`（文件名可配） | ✅ |
| Windsurf | `.windsurf/rules/` | ✅ |
| Cline | `.clinerules/` | ✅ |

**桥接用 import，不用软链**：

```markdown
<!-- CLAUDE.md：两行即可 -->
@AGENTS.md

## Claude Code 专属
（仅此工具需要的补充）
```

- **为什么不用软链**：`ln -s` 在 Windows 上需开发者模式或管理员权限；CI 容器与 zip 下载还会把它拍平成普通文本。**import 跨平台一致，且允许追加工具专属段**——软链做不到。
- 这是 Anthropic 官方文档推荐的做法，非自创。

**上下文预算纪律**：
- 根 `AGENTS.md` 控制在 **200–300 行以内**；超出的按主题拆到 `docs/rules/*.md`。
- **import 不省 context**（启动即全量加载），只有**路径 / glob 作用域**才真正省。

### 11.6 「上下文不是配置」——强制项必须落成门禁

官方文档说得直白：规则文件是**作为消息投递给模型**的，模型「读到并试图遵守」，**没有任何保证**。

所以纪律必须分两级：

| 级别 | 机制 | 适用 | 例子 |
|---|---|---|---|
| **文档级**（提醒） | `AGENTS.md` / rules 里的句子 | 「我们一般这么做」 | 命名风格、提交信息格式 |
| **门禁级**（强制） | hook / 校验脚本 / 权限配置 | 「无论如何都必须」 | 提交前跑测试、上游只读、禁改 `contracts/` |

**判据**：同一个规则如果在文档里写了三遍仍未被遵守——**它就不该待在文档里，该做成门禁**。

> 这正对应 §5 的审核门禁与 §7 的校验脚本：**校验脚本才是门禁，`AGENTS.md` 只是提醒。**

## 12. 多源 skill 供给与准入

> §7 讲「三层供给」（L1 通用 / L2 领域 / L3 契约）；本节讲**无论哪一层、哪个渠道来的 skill，都过同一道闸**。

### 12.1 渠道现状（2026-09 实测）

| 类型 | 代表 |
|---|---|
| 官方目录 | `github.com/anthropics/skills`、`github.com/openai/skills` |
| 开放注册表 | **`agentskills.io`**（Agent Skills 规范，Anthropic / OpenAI / Google ADK / Agno 采用） |
| 聚合市场 | `skills.sh`(2.6k+)、`SkillsMP`(145k+)、`AgentSkillsHub`(117k+)、`claudskills.com`(67k+)、`cocoloop hub` |
| 社区集合 | `obra/superpowers`、`alirezarezvani/claude-skills`（338 skills · 支持 13 工具转换）、awesome 列表 |

**skill 已成为开放标准**（agentskills.io，2025-12 起）——与 `AGENTS.md` 一样可跨工具，且有现成转换工具（`convert.sh --tool all`）。

### 12.2 风险（实测数字）

**Snyk ToxicSkills 审计（2026-02，抽样 3,984 个 skill）**：

> **36%（1,467 个）至少有一个安全缺陷；13.4%（534 个）存在严重问题；76 个已确认恶意**（凭证窃取、后门、数据外泄）。

skill 是**可执行的指令 + 脚本**，能碰文件系统、shell 与密钥——**它不是文档，它是依赖**。

### 12.3 准入四步（硬性）

```text
多源渠道 → 隔离暂存 + 安全审计 → 归一化入库（vendor）→ 允许使用
                  ↓ 未过
                拒收，不入库
```

三条硬规则：

1. **不许「直接安装生效」**——一律先进隔离区，审计通过才移动。
2. **一律 vendor 进仓库**（`skills/`），**不引用外部路径**——否则云电脑拉不到、上游删除即断供。
3. **记 provenance**：来源 URL + commit / 版本 + 审计结论 + 审计日期，落在 `skills/PROVENANCE.md`。

**✅ 审计方式已定（v0.11 · 裁决 8）**：**引入自动扫描**——`skill-security-auditor` / **Cisco Skill Scanner** / Snyk Agent Scan（择一并用），**叠加人工读 `SKILL.md` 与 `scripts/`**（自动化扫不出的语义级风险，靠人看）。

> **启用时机**：**随 skill 安装一并启用**，即与 §9.0 规划冻结同步。规划期不装 skill，也就不扫——**工具与它守护的对象同时进场**，不空转。

### 12.4 自建 skill 的两条纪律

- **必须人审，不许全自动生成**。ETH Zurich 研究（2026）：LLM 自动生成的 `SKILL.md` 使 agent 成功率下降约 3%、token 成本上升约 20%。**人写的 do / don't 规则持续优于 AI 生成。**
- **确定性步骤写进脚本**，不要靠模型推理（跑 linter、查类型、校验命名——一律脚本化）。

## 13. 多环境（云电脑 / CI）与状态持久化

云机与本地最大的区别：**环境是临时的，随时可销毁**。三条纪律：

1. **环境即代码**——工具链固化进 `devcontainer.json` / `Dockerfile` / 初始化脚本（Godot 版本、Python、Node、blender-mcp…），一键重建。**不依赖「我这台机器装过什么」的记忆。**
2. **状态只认 git**——云机上一切产物必须提交推送。**未推送 = 没做。**
3. **凭证绝不入库**——SSH key / token / API Key 走环境变量或密钥管理，`.gitignore` 兜底。（与既有的「不粘贴凭证、走浏览器授权」习惯一致。）

**附带红利**：云机 + 沙箱天然适合跑**只读审核 agent**，风险隔离比本地更彻底。

### 15.1 推导类结论必须留"可复核"标记（v0.12 新增）

> **依据**：§14-13（`tasks/` `records/` 归属）在 v0.11 由我**自行推导**，v0.12 复核时发现推导不成立——**唯一错误是「产生方」这个词被读成了「执行位置」**。文档本身没错字、无矛盾、引用也一致，**全文检索救不了它**。

故立两条：

1. **区分「大人裁决」与「我的推导」。** §14 台账里，凡非大人明确表态、由我推导得出的项，**必须标注来源**。理由：推导是我的产出，本就该被复核；混记为「裁决」会让复核无形中被禁止。
2. **抽象判据要标注它的读法。** 凡用抽象词做归属 / 分类推导（「产生方」「归属方」「职责」…），**当场写清这个词取哪一义**，并在旁注**另一种读法下结论会不会变**。
   > 自检句：**「这个词有没有第二种读法？第二种读法下，结论会不会变？」**

**错误分类对照**（三类，不会互相覆盖）：

| 类型 | 例子 | 能否靠全文检索发现 |
|---|---|---|
| 引用未同步 | §3 契约归属、§0 hub 结论 | ✅ 能 |
| 事实未复核 | 断言 hub 无游戏 skill | ❌ 不能，须实查 |
| **推导用词不严** | §14-13「产生方」= 执行位置？ | ❌ 不能，须自问读法 |
