## 0. 本文件解决什么缺口

上游 §3 把服务端写得很细（九类进程 / 三层协议 / 关键时序 / 分线扩容 / 反外挂 / 运维）。但**三件事没落**：

1. **「现在」长什么样** —— 上游 §3.1 给的是**设计态**九类进程，「起步态」只在括号里一句话，没有「当前该建几个进程」的明确落点；
2. **「什么时候」拆** —— 上游 §3.5 的分线扩容表按**规模**（内部测试 / 小规模上线 / 中期 / 远期）划分，**不按里程碑划分**，与 `ROADMAP.md` 的排期对不上；
3. **归置缺口** —— `PROJECT-STRUCTURE.md` 管的是 **UE 工程**，`server/` 在其中只占一行（「服务端 · Go」）；**「服务端进程形态与拆分时机」在 guild 侧无落点**。ADR-0014 裁定 protoc 归 M4 时，依据散落在上游三节里，无本地指针。

> **本文件 = 服务端的单一入口。**
> 与 `MOBILE-PLAN.md` 同构：那份答「手机端放哪 / 怎么出包」，本文件答「服务端拆不拆 / 何时拆」。

## 1. 现在是什么形态

### 1.1 设计态：九类进程（**上游已裁，本文件不重开**）

上游 §3.1 划定九类进程。**这是设计蓝图，不是施工顺序。**

| # | 进程 | 数量 | 职责 | 技术 |
|---|---|---|---|---|
| 1 | **Gateway**（网关） | 1-2 | 连接管理、鉴权、消息路由、限流、反外挂卡点 | Go |
| 2 | **Login**（登录服） | 1 | 账号注册/登录、令牌签发、服务器列表 | Go |
| 3 | **World**（世界服） | 1 | 分线/分流调度、场景分配、跨场景传送 | Go |
| 4 | **Scene / DS**（场景服） | N | 移动、战斗、AI、掉落、场景内交互 | **UE5 Dedicated Server** |
| 5 | **Game**（业务服） | 1-N | 角色数据、背包、装备、境界、技能学习 | Go |
| 6 | **Social**（社交服） | 1 | 好友、宗门、师徒、道侣、聊天 | Go |
| 7 | **Economy**（经济服） | 1 | 交易、拍卖行、邮件、灵石 | Go |
| 8 | **Rank / Scheduler**（排行与定时） | 1 | 排行榜、定时任务（活动、赛季、结算） | Go |
| 9 | **GM**（后台服务） | 1 | 运营指令、封禁、补偿、审计 | Go |

> **口径**：九类中 **8 类是 Go 进程**（1/2/3/5/6/7/8/9），**第 4 类是 UE 进程**（DS）。`ENVIRONMENT.md` §1 「Go 行」写的「八类进程」即指此。

**上游定的第一原则**（§3.1 原话）：

> ### 「逻辑上是分布式的，部署上可以先跑在同一台机器。」

### 1.2 起步态：**8 合 1**，只留 DS 独立

上游 §3.1「起步部署（阶段 0-1）」：

| 项 | 起步做法 | 为什么 |
|---|---|---|
| **1 / 2 / 3 / 5 / 6 / 7 / 8 / 9** | 全部**合并进一个 Go 进程** | 单体但**模块化**；收敛成本 |
| **4（Scene / DS）** | **独立** | 它是 **UE 进程**，与 Go 物理上不同源 |

> **上游原话：「收敛成本，不收敛设计。」**
> 即：**部署上合并，代码结构上按九类划分** —— 保证将来拆的时候是「挪文件」而不是「重写」。

### 1.3 当前实际（2026-09-28 实测）

| 项 | 现状 |
|---|---|
| `qiuyuan-dalu/server/` | **只有 `.gitkeep`** —— 尚无一行 Go 代码 |
| M1 的进程形态 | **1 个 Go 进程**（Gateway + Login + Game 三角色模块）**+ UE5 客户端** |
| UE DS | **M1 不起**（M1 Out of scope 明写「世界、场景、移动 → M4」） |
| 跨进程调用 | **零** —— 全部是进程内 Go 调用 |

> **M1 服务端的具体交付**：`MULTI-AGENT-DEV-PLAN.md` §13 定为「网关 + 账号服务 + 角色服务」三个模块，跑在一个进程里。
> **故 M1 与「分布式」无关** —— 这是 ADR-0014 判定 protoc 归 M4 的直接依据。

## 2. 现在必须守的纪律：**四条拆分前提**

上游 §3.1 把以下四条写进代码规范。**它们不是将来的事 —— 第一天写代码就生效。**

| # | 前提 | 为什么它决定将来能不能拆 |
|---|---|---|
| ① | **禁止全局单例**（用依赖注入或显式传参） | 单例是**进程内的隐式耦合**，拆进程时无处安放 |
| ② | **玩家数据不驻留进程内存**（每次从 Redis/MySQL 读，或走短生命周期缓存） | 数据留在内存 → 拆开后两边各一份 = **双真源** |
| ③ | **模块间只通过接口通信**（不直接访问别的模块的内部结构） | 直接访问内部结构 → 拆开时**改动面不可控** |
| ④ | **所有跨模块调用走同一条内部 RPC 抽象** | 抽象在，将来换网络调用**零改动** |

> **第 ④ 条与本项目的一处裁决直接相关**：`ADR-0014` 判 protoc 归 M4，依据正是「**『抽象』≠『网络』**」——
> M1 写 Go 接口即可，接口签名与将来的 `.proto` 不冲突；**等第 ④ 条真要走网络时才需要 protoc**。

**验证方式（M1 起）**：这四条中 ①②③ **可机械校验**（扫全局变量 / 扫跨模块 import），够格写成门禁规则 —— **M1 建 `server/` 时评估**（同 `PROJECT-STRUCTURE.md` §7.3 纪律 1 的处理方式）。

## 3. 什么时候拆（**按里程碑，不按规模**）

上游 §3.5 按规模划分；本文件把它**对齐到 `ROADMAP.md` 的里程碑**：

| 阶段 | 进程形态 | 触发事件 | 此时才需要 |
|---|---|---|---|
| **M1 – M3** | **1 个 Go 进程** | — | Go / Luban |
| **M4** | **Go + UE DS**（首次两进程） | 场景服独立成进程，`Scene ↔ Game` 真走 gRPC | **protoc + gRPC 插件**（ADR-0014） |
| **小规模上线** | 1 网关 + N 个 DS | 单 DS 装不下了 | Docker Compose |
| **中期** | 网关集群 + World 调度 + 多机 DS | 单机装不下了 | 服务发现 / 监控 |
| **远期** | 按洲域分区（北桢/南明/东曜/西陵/不见海各一组） | 商业化 | K8s |

> **拆分的代价随形态递增**：M4 只是「多起一个进程」；中期才涉及服务发现。**故不必预拆**，与 `PROJECT-STRUCTURE.md` §5「M1 不拆模块」同一判据。

### 3.1 上游的分线扩容表（§3.5 原文）

| 规模 | 架构 | 场景服容量 |
|---|---|---|
| 内部测试 | 1 个 Go 进程 + 1 个 UE DS | ≤ 64 人/场景 |
| 小规模上线 | 1 网关 + 多 DS 实例（同机多进程） | 100-200 人/实例 |
| 中期 | 网关集群 + World 调度 + 多机 DS | 分线（同地图多实例） |
| 远期 | 按洲域分区（北桢/南明/东曜/西陵/不见海各一组） | 跨服战场 / 跨服拍卖 |

### 3.2 一个必须说清的真相：**千人同屏是用分线伪造的**

> **上游 §3.5 原话**：**单 UE DS 进程承载 100-200 人已是现实上限**（含 AI 与战斗）。所以「大世界千人同屏」在 UE 栈下是**用分线伪造的** —— 玩家看到的「同一张地图」，实际是**多个实例 + 无缝切换**。这是成熟做法，不必羞耻。

**三条承载要点**（上游 §3.5）：① 非战斗逻辑**不进 DS**（背包/宗门/经济全提到业务服）；② **AI 分级**（远处用状态机，近处才用行为树）；③ 掉落与经验由 DS **上报**、业务服**结算**，**DS 无状态化**以便随时重启。

> **对设计的约束**：这条直接决定「同场景可见玩家 ≤ 30」等资产预算取值（见 `MOBILE-PLAN.md` §3.1）——
> **分线不是妥协，是既定架构**；玩法设计（宗门战、跨服拍卖）必须长在这个前提上。

## 4. 内网链路（**与契约的分工**）

上游 §3.2 定「三层通信」，本项目按**谁服务谁**分工：

| 链路 | 协议 | 归谁 | 现状 |
|---|---|---|---|
| **客户端 ↔ Gateway** | TCP + UDP/KCP + Protobuf | **契约 §1**（现取 **WS + JSON**） | ⚠️ **层级差已登记**，M2 前须裁（ADR-0014 §附带） |
| **Gateway ↔ 业务服** | gRPC + Protobuf | ★ **本文件** | M1 为**进程内 Go 调用** |
| **场景服 ↔ 业务服** | gRPC + Protobuf | ★ **本文件** | M4 起（DS 独立后） |
| 业务服 ↔ 数据库 | MySQL 协议 | ★ **本文件** | 只在业务服访问 DB |

> **边界口诀**：**「出网的」归契约（客户端能看见的），「内网的」归本文件。**
> M1 阶段**内网两条链路都不存在** —— 合并成一个进程后，它们退化为函数调用。故 protoc 不在 M1 账上（`ENVIRONMENT.md` §4.2）。

**上游的两条消息设计约定**（承接，M4 前不展开）：① 所有消息带 `role_id` + `seq`（序列号）+ `timestamp`；② 客户端请求-响应成对，**超时重试须有幂等键**（防重复扣费 / 重复发奖）。

## 5. 部署与运维（起步档）

| 项 | 选型 | 说明 |
|---|---|---|
| 服务器 | 云主机（GPU 机型跑 DS） | DS 需独显；业务服普通机型 |
| 容器 | **Docker（业务服）+ 裸机（DS）** | DS 对 GPU 直通敏感，**优先裸机** |
| 编排 | **Docker Compose（起步）→ K8s（后期）** | ⚠️ **起步别上 K8s**，2-3 人维护不动 |
| 监控 | Prometheus + Grafana | 进程存活、延迟、在线数、报错率 |
| 日志 | 集中收集（Loki / ELK） | 排查线上问题 |
| 备份 | MySQL 每日全量 + 实时 binlog | **丢档是 MMO 头号事故** |
| 告警 | 钉钉 / 企业微信机器人 | 进程宕机、DB 异常、异常交易 |

> **本项目落地节奏**：M1 只需**本机跑一个 Go 进程** —— Docker Compose 都不必上（`ENVIRONMENT.md` §1 已列其为待装，**触发点是「小规模上线」**）。
> **反外挂**（上游 §3.6）属**运营层**，收口在 **M17**，本文件只登记其存在。

## 6. `server/` 内部结构 —— ✅ **已裁：技术模块切**（ADR-0016）

### 6.1 裁决

**`server/` 按技术模块切一级目录** —— 子树名 = **上游 §3.1 九类进程中的 Go 类**（进程名即目录名）。

**判据**：目录结构回答「**这段代码跑在哪类进程里**」。将来拆进程时**挪目录即拆分** —— 不改包名、不改 import 路径。这是上游 §3.1「**收敛成本，不收敛设计**」在目录层的落点。

```
server/
├─ cmd/qydalud/main.go      ← 单进程入口（M1 一个 main —— §1.2「8 合 1」）
├─ internal/
│  ├─ gateway/              ← 进程 1：对外唯一入口（连接 / 鉴权 / 路由 / 限流）
│  ├─ login/                ← 进程 2：登录服（M1 交付=「账号服务」）
│  ├─ game/                 ← 进程 5：业务服（M1 交付=「角色服务」切片）
│  └─ platform/             ← ★ 技术横切底座（**非进程**）：DB / Redis / 配置 / 内部 RPC 抽象（§2 第 ④ 条）
├─ go.mod
```

**M1 只建三个进程包 + 一个底座**：

| 目录 | 对应进程 | M1 交付（`MULTI-AGENT-DEV-PLAN.md` §13） |
|---|---|---|
| `internal/gateway/` | **Gateway**（1） | 网关：连接 / 鉴权 / 路由（最简） |
| `internal/login/` | **Login**（2） | **账号服务**：注册 / 登录 / 登出 |
| `internal/game/` | **Game**（5） | **角色服务**：建号 / 属性面板（薄切片） |
| `internal/platform/` | —（横切） | DB / Redis 连接 / 配置加载 / **RPC 抽象**（第 ④ 条） |

> **命名口径**：目录取**上游进程名**（`login` / `game`），**不取 M1 交付别名**（「账号服务」/「角色服务」）。
> 理由：技术模块切的价值就在「**目录 = 进程**」—— 将来 `login/` 长为完整登录服、`game/` 长为完整业务服（背包 / 装备 / 境界 / 技能），**目录名不用改**。
> 与 §1.3 已写的「Gateway + Login + Game」一致。（**注**：本节 v1 草稿曾写 `account/` `role/`，与 §1.3 不符，已更正。）

### 6.2 与方案 §2.1「owner 领地」如何叠加（**曾误判 · 重点更正**）

方案 §2.1（v0.11）**已定**：「**独占领地 = 模块子树，不是顶层目录**」，Go 侧写权落 `server/internal/<module>/`，判据「**一列一主，同一时刻同一子树只有一个 agent 有写权**」。

**两套坐标正交 —— 不是二选一，也不互相覆盖**：

| 坐标 | 回答什么 | 取值 |
|---|---|---|
| **技术模块**（本裁决 · **一级目录**） | 代码**跑在哪类进程** | `gateway` / `login` / `game` / … |
| **owner 领地**（§2.1 · **写权**） | **谁有权写** | `world` / `combat` / `scene` / `ui` |

**叠加三规则**：

1. **一级按技术模块切**（本裁决）—— 目录表达**运行时归属**；
2. **写权边界在技术模块内声明** —— 某子树**当前归哪个 owner**，落在 `server/internal/<module>/OWNERS`（M1 建骨架时评估是否落地，同 §2 ①②③ 的门禁化处理）；
3. **确需再分时，才在技术模块内建 owner 子包**（如将来 `game/` 内出现 `game/combat/` 战斗结算）—— **M1 不建**（**不留空壳**，同方案 §3.2）。

> **M1 为何不实操**：M1 Go 侧**只有一个 owner** —— `world`（数据侧 + 三个服务模块，见方案 §2.1「M1 只用到 `world` + `ui`」）。单人项目下**写权在 M1 不产生实际冲突**，故**规则定死、目录不预分**。

### 6.3 与 §2.1 的路径示意对不上 —— 已回写

方案 §2.1 表格「独占领地」列原写 `server/internal/world/` `combat/` `scene/`，且**自注「上表的具体路径待 M1 骨架建立时落实」**。本裁决即那次「落实」，**故已回写 §2.1**：Go 侧领地由「`internal/<owner>/`」修正为「**一级 `internal/<进程>/` + 写权声明**」。

> **owner 体系不动** —— 四个 owner（world / combat / scene / ui）及其覆盖的 14 模块**不变**；变的只是**跨端「模块子树」在 Go 端的具体形制**。

> **状态**：**已裁**（**ADR-0016**）。M1 In scope 第 0 项「建工程骨架」的**服务端侧判据至此齐备**。
