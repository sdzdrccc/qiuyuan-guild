## 三、机制落地要点

### 1. ③ `PENDING_RULES` —— 「写了却未加」不再静默
每个 `check-*.js` 顶部加常量；**非空 → 启动打印（warn）**，`--strict` → err。
**硬约束**：每项**必须带 `from`（来源记录号）**，否则打印 `⚠缺来源` —— **防它变成「永久待办黑洞」**。

> `X-0015` §二-3 的根因是「**承诺写在下游文档里，脚本归 guild ⇒ 两不管**」。此常量就是那个落点。

### 2. ⑦ 契约回执 —— 契约缺口的**前置化上报**
`check-records.js` **`C6`**：dalu 的 `T-*.md` 须有**非空**「契约回执」节（**写「无」也算**）。
> `X-0015` §五-⑦ 的真空：方案 §5.2 的「审核者 = 下游消费者」表**没有任何一行**覆盖「**guild 的契约由谁审**」。

### 3. ⑥ 审核分级进模板 + `C4` 升级
`CONVENTIONS.md` §5.2 的「审核」节增 **`触发级别` + `依据`**；
`C4` 从「须含大人」**升级**为「**级别须声明，且与改动面匹配**（改 `contracts/` 的必须 **L3**）」。

### 4. `WAIVED` 豁免花名册 —— 补「书面豁免」无实现位
`X-0015` §六 说存量「**可书面豁免**」，但**脚本里没有任何实现位** ⇒ 存量项会**永久黄**，与「不许给未来埋雷 / 不许永久误报」**自相矛盾**。
现补：`WAIVED = { commits: {…}, records: {…} }`，命中 → 从 backlog 移入「**已豁免**」并**原样打印**（仍可见，只是不报 warn）。
**判据**：**豁免也要留证**（理由 · 裁定人 · 日期）—— 与 `RETIRED`（退役名花名册）同构。

### 5. 审阅流程成文
`docs/REVIEW-PROCESS.md` —— 五步流程 / 判据来源表 / 输出模板 / 三条设计纪律 / 五个实战坑 / 分流与分工。
> **它是「流程」，规则仍在方案 §5 与 `CONVENTIONS.md` §5** —— 单一真源，不复写。

### 6. 审阅 skill（**大人这次的直接诉求**）
`qiuyuan-review-pipeline`（用户级）—— 在**任何 agent 会话**里一句话「**审阅 `<仓> <范围>`**」即加载流程执行。
它是 `REVIEW-PROCESS.md` 的**可执行封装**，**不是第二真源**（冲突以 guild 为准）。

### 7. 门禁判据修正（3 处 · 全部由本轮实测暴露）

| # | 判据 | 原来的病 | 修法 |
|---|---|---|---|
| 1 | `fileIsFresh()` | 取「**最后一次改动**」的提交判存量 / 新增 | 改取「**首次出现**」（`--diff-filter=A`）—— 否则「老卡被顺手改一行」会被误判为新增（实测 `T-0010` / `T-0017` 从 `warn` 变 `err`） |
| 2 | `reviewSection()` | 标题**含**「审核」即认作审核节 | 收严为「**主体名以「审核」开头**」（新增 `headingName()`）—— 否则 `# X-0016 … ⑥ 审核分级` 这种大标题被误认 |
| 3 | `hasScoreLanguage()` | 豁免词不足 | 加「**否决 / 不采用 / 取代 / 拒绝**」—— `X-0002` 审核节里「（其他 agent **评分**）**否决**并给出替代品」被误判为评分（**同一篇的第二次**误报） |

> **三条都符合 `X-0015` §四-1「误报率高的门禁 = 没有门禁」** —— 修完 `check-records` 从「1 错」回到「**通过**」。
> ★ **第 2 条还顺带修正了一处漏报**：收严后 `X-0002` 的**真**审核节才被正确识别（此前定位到了错的节，导致它被误报「未声明触发级别」；现查明其审核节含 `L3`，**本身合规**）。
