## 关键判断（四条）

### 一、裁决：一级按**技术模块**切，子树名 = **进程名**

`server/` 一级目录 = 上游 §3.1 九类进程中的 **Go 类**（**进程名即目录名**）。**判据**：目录回答「**代码跑在哪类进程**」—— 将来拆进程**挪目录即拆分**，不改包名与 import 路径（上游 §3.1「**收敛成本，不收敛设计**」）。

M1 落形（`SERVER-ARCH.md` §6.1）：

| 目录 | 对应进程 | M1 交付（方案 §13） |
|---|---|---|
| `internal/gateway/` | Gateway（1） | 网关：连接 / 鉴权 / 路由 |
| `internal/login/` | Login（2） | **账号服务**：注册 / 登录 / 登出 |
| `internal/game/` | Game（5） | **角色服务**：建号 / 属性面板 |
| `internal/platform/` | —（横切） | DB / Redis / 配置 / **RPC 抽象**（第 ④ 条） |

> **命名取进程名**（`login` / `game`），**不取** M1 交付别名（「账号服务」/「角色服务」）—— 目录随进程长大而**不改名**。

### 二、**推翻我上一轮 §6 草稿的两处错**（自查发现）

| # | 错处 | 更正 |
|---|---|---|
| 1 | **出处引错** —— 把「agent 领地」的出处写成方案 **§10** | §10 **实为「反模式清单」**，不含领地划分。真出处是 **§2.1「纵向：4 个模块 owner」** |
| 2 | **目录名写错** —— 草稿写 `account/` `role/` | 与 §1.3 已写的「**Gateway + Login + Game**」不符 → 更正为 `login/` `game/` |

**错的根因（留痕）**：草稿**未核 §2.1 原文**就下了「两套划分互不相同」的结论。核后才发现 —— §2.1（v0.11）**本就已定**「**独占领地 = 模块子树，不是顶层目录**」，Go 侧写权落 `internal/<module>/`，且**自注「待 M1 落实」**。**两者从来不是二选一。**

### 三、真相：**两套坐标正交，不是互斥选项**

| 坐标 | 回答什么 | 取值 | 本轮变化 |
|---|---|---|---|
| **技术模块**（ADR-0016） | 代码**跑在哪类进程** | `gateway` / `login` / `game` / … | **一级 = 本裁决** |
| **owner 领地**（方案 §2.1） | **谁有权写** | `world` / `combat` / `scene` / `ui` | **体系不变** |

**叠加三规则**：① 一级按技术模块切；② owner 写权在技术模块内**声明**（`OWNERS`）；③ 确需再分时才建 owner 子包（**M1 不建**，不留空壳）。

> **M1 为何不实操**：M1 Go 侧**只有一个 owner**（`world`）—— 写权不产生实际冲突，故**规则定死、目录不预分**。

### 四、连带：**回写方案 §2.1 的领地路径**

§2.1「独占领地」列原写 `server/internal/world/` `combat/` `scene/`（v0.11 **示意**，自注待落实）。本裁决即那次落实 → Go 侧形制正式定为「**一级 `internal/<进程>/` + 写权声明**」。**owner 体系与 14 模块覆盖度不变。**

> **可复用判据（留痕）**：目录切分该按「**运行时归属**」还是「**写权归属**」？答案是**两个坐标分层** ——
> **物理目录表达运行时**（可拆可挪），**写权用声明**（可变可换主）。把两者压成一层，必牺牲其一。
