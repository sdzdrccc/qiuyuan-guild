## 一、裁决落地了什么

| # | 项 | 契约侧 | 下游侧（dalu） |
|---|---|---|---|
| 1 | **境界段真源换表换形** | 数据契约 §4.1 **删 `shenshi_start` / `shenshi_step` 两列**（原来要在按层表里十行抄同一对数 = 两处真源）；§4.2 `RealmConfig` **新增一列 `shenshi_step`** ＝ 本境每层加值 | `qydl_realm_level_config.csv` 20 → **18 列**；`qydl_realm_config.csv` 新增一列；服务端 `deriveShenshiLadder()` 起服时**按台阶累加**派生成表 |
| 2 | **算法** | `境界段(realm, layer) = Σ 从炼气一层累加到本台阶的每层加值`（取代「起点 + (层-1) × 增量」） | 唯一算法一份，建角与读角色共用；查不到 = **无值**，不产生"强度 0" |
| 3 | **逐档翻倍 · 九境填满** | §4.2 附九境现值表：100 / 200 / 400 / 800 / 1600 / 3200 / 6400 / 12800 / 25600 ⇒ **建角 100**、炼气圆满 1000、筑基圆满 3000、金丹圆满 7000、**渡劫圆满 511000** | CSV 已填；★ 明写「按翻倍推的第一版可跑数，非世界观给定值」 |
| 4 | **突破不额外大涨** | 曲线连续（炼气圆满 1000 的下一档即筑基一层 1200）；原「起点」列带来的跨境落差随列一起消失 | 同 |
| 5 | **未定哨兵 `0/0` → `-1`** | ★ 累加口径下 **0 是合法语义**（"这一境不再涨"），不能再当"没配" ⇒ 换成不可能是真值的 `-1`；下游校验三条：只许正数或 -1 · **-1 必须是后缀** · **已定各境严格递增**（「更高境界加的值更多」的机器化） | `deriveShenshiLadder()` 三条全部启动期执法；假表用例继续兜 -1 语义（现值虽已填满） |
| 6 | **余量上限 = 境界段** | §3.3 `shenshi_pool_factor` 现值 **10 → 1**（★ 键**保留**当倍数旋钮 ⇒ 放大只改表不改码） | 代码仍乘该系数（现值 1）；净效果：强度 ×10 与系数 ÷10 对冲 ⇒ **建角余量仍是 100** |
| 7 | **协议一字未动** | 协议 v0.13 只改**来源叙述**与一处列名；`shenshiIntensity` / `shenshiFromRealm` / `shenshiCultivation` / `shenshiPool` / `shenshiPoolMax` 五键、消息方向、单位**全部原样** | 客户端解析未改；仅画稿/演示数值随量级换（`285 / 300`） |

★ **顺带订正一处旧账**：余量结算列在契约里一直写 `shenshi_pool_updated_at`，而下游已按自己的命名规范（**epoch 毫秒 ⇒ `_ms`**）改成了 `shenshi_pool_updated_ms`（dalu 迁移 `0009`，其 `DATA-LAYOUT` 有四·补判据与回读留证）。本卡随批把数据契约 §3.1 与协议 §3.3.1 两处**改成 `_ms`** —— 属对齐既有实现，不改语义。
