## 起因

大人原话：

> 「protoc 有什么用」

这是个**理解性问题**，但核对真源时发现**我自己台账里有一处判断错了**。

## 关键判断（五条）

### 一、protoc 是**代码生成器**，不是运行库

一份 `.proto`（只定义消息与字段）→ protoc → **各语言代码**（Go / C++ / Python）。同一份定义两侧各自生成，**字段类型永不漂移**。

**它解决的痛点**：客户端（C++）、服务端（Go）、工具（Python）三方手写结构体，**改一个字段要改三处**，且**没有任何机制保证三处一致**。

### 二、本项目里它管**内部链路**，不管客户端

上游《技术架构》**§3.2 通信协议（三层）**：

| 链路 | 协议 | 用 protoc？ |
|---|---|---|
| 客户端 ↔ Gateway | TCP + UDP/KCP + Protobuf | ✅（目标形态） |
| Gateway ↔ 业务服 | **gRPC + Protobuf** | ✅ |
| 场景服 ↔ 业务服 | **gRPC + Protobuf** | ✅ |

而契约 §1 定的是 **客户端 ↔ 服务端 = WebSocket + JSON**。

### 三、原判的两条错（本轮更正）

| # | v0.21 原判 | 真源实况 |
|---|---|---|
| ① **引用错误** | 「**契约层**已定 gRPC + Protobuf」 | 契约定的是 **WS + JSON**。gRPC + Protobuf 出自**上游 §3.2**，管**内部链路** |
| ② **时序错误** | 「M1 的首个协议就要落地」→ 故需 protoc | M1 首个协议（`login` / `register` / `create_character`）走**契约 §1 的 WS + JSON**，与 protoc 无关 |

### 四、决定性依据：**M1 的进程形态**

上游 **§3.1「起步部署」** 明写：

> 1、2、3、5、6、7、8、9 **全部可合并在一个 Go 进程里**（单体但模块化），只把 **4（场景服）**独立出来。

→ M1 阶段 `Gateway → Login` / `Gateway → Game` 是**进程内 Go 函数调用**，**不跨网络 → 无 gRPC → 无需 protoc**。

**protoc 的真实触发点 = M4**（场景服 UE DS 独立成进程、`Scene ↔ Game` 走 gRPC 时）。

> **判据复用**（ADR-0010 §四）：「不做」将来会推翻已写的东西 → 现在做；将来只是补配置 → 现在不做。
> protoc 属**第三类** —— 「将来才需要，**且现在不做也不影响已写的东西**」：
> 上游 §3.1 拆分前提第 ④ 条要求「所有跨模块调用走同一条内部 RPC **抽象**」——
> **「抽象」≠「网络」**，M1 用 Go interface 即可，**接口签名与将来的 `.proto` 不冲突**。

### 五、附带发现：一处协议层级差（**待裁 · 不阻塞 M1**）

| 链路 | 上游 §3.2 | 契约 §1 |
|---|---|---|
| **客户端 ↔ Gateway** | **TCP + UDP/KCP + Protobuf** | **WebSocket + JSON** |
| Gateway ↔ 业务服 | gRPC + Protobuf | **未覆盖** |
| 场景服 ↔ 业务服 | gRPC + Protobuf | **未覆盖** |

**判断（不擅自改）**：**可能不是矛盾，而是分阶段** —— 契约 §0 自述「从 Codex 原型提炼」，原型（Godot · 验证方）就是 WS + JSON；上游 §3.2 是**目标形态**。
但**上游未写明「原型期先用 WS + JSON」这句过渡** → 属**须补的一句话**，不是须裁决的冲突。

**处置**：登记 `protocol-contract.md` §8，**M2 前须裁**（M2「首战」才真正用 UDP 实时同步）。

> ⚠️ **本条的教训与坑 16 同源**：**判据要落在「它到底服务哪条链路」上**。
> v0.21 我只看到「契约里有个 `gRPC + Protobuf` 的字样在 ENVIRONMENT 里」，没回去核对**它是谁的协议** ——
> 与 MSVC 那次「拿目录名当版本号」是同一类错：**没落到真源的那一个字段/那一条链路上**。
