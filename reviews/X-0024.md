## 一、做了什么

### 1. 这一批从哪来：**下游的「契约回执」积压**

依 `CONVENTIONS.md` §5.4 机制⑦，下游每张 `T-*` 都带「**契约回执**」上报缺口，且**只报不改**。
到 2026-10-01，三张记录累计上报 **8 处**：

| 来源 | 上报内容 |
|---|---|
| `T-0022` | 契约 §4 缺「读配置表」端点（GM 看不到配置表）；`/api/stats` 需增字段 |
| `T-0023` | §2.1 的 `accountId` 冗余（**安全**）；`error` 回包未被 §3 定义；`data` 内字段命名无规则；封禁具名 vs 防枚举的取舍；`/api/stats` 的 `connections` |
| `T-0024` | `accountId` 冗余**已实现并被端到端验证**；§2.1「回落口径待裁」与 `data-contract` v0.7 **矛盾**；`create_ok` 是否带 `origin`（详案与契约冲突） |

★ **本记录的意义**：验证「**下游自动上报 → 上游集中裁定**」这条回路**真的转得起来** ——
而不是「下游报了一堆，上游一直不动」。

### 2. 八条裁决（正文见 `DECISIONS.md` **ADR-0023**）

| # | 问题 | 最优解 |
|---|---|---|
| **①** | ★★ **`accountId` 出现在请求体里**（`create_character` / `list_characters`）—— **安全缺口** | **从请求体删除**；§1 明写「身份一律取自会话，请求体不携带」 |
| **②** | §2.1 仍写「回落口径**待裁**」，而 `ADR-0022` 已裁、`data-contract` 已升 v0.7 | **同步**为「回落 = 落凡体（ADR-0022）」 |
| **③** | §3 **未定义「协议层错误」回包** | **新增 §3.0 通用 `error`** + 写明与 `*_fail` 的**分工** |
| **④** | §4 `/api/stats` 缺 `connections` / `loggedIn` / `sources` | **补入**，并**明文区分 `online`（已进世界）与 `connections`（连着的人）** |
| **⑤** | §4 缺「读配置表」端点 | **新增** `GET /api/gm/config` 与 `GET /api/gm/config/{table}` |
| **⑥** | §1 只规定了 `type` 的风格，**没说 `data` 内字段叫什么** | **补**「`data` 内一律 camelCase」 |
| **⑦** | 「防枚举」与「封禁具名」看似矛盾 | **确认**为有意的三段式；★ 并**补上第二道防线**：**耗时也必须相当**；★ 补禁令：**不得对不存在的账号回任何具名原因** |
| **⑧** | 详案要求 `create_ok` 带 `origin`，契约 §5.1 没有 | **加进协议 §5.1 角色对象**；**`data-contract.md` 不动** |

### 3. ★★ 三条最该记住的

**(a) ① 是安全缺口，不是洁癖。**
`accountId` 服务端**在会话里已经有了**；请求里再带一份，就是给客户端一个**可随便改的身份声明**。
照契约实现就会写出「**能给别人账号建角**」的漏洞 —— 下游 `T-0024` 已经**实现并被端到端验证**过这条防护。

★ **并顺手升级了下游的正确行为**：契约删掉该字段后，最优实现从「发现伪造就拒绝」
变为「**根本不读它**」。**拒绝仍需先解析、且会让旧客户端报错；不读才彻底。**

**(b) ★ 范围闸门：只清 M1 域，其余只登记。**
「身份字段出请求体」这条原则若**全局生效**，会牵连 §2.5 物品 / §2.6 储物 / §2.7 功法任务 / §2.8 社交
里大量的 `characterId` —— 那些属 **M2 / M5 / M7 域**，且**牵着「角色选择 / 多角色」等未裁问题**。
⇒ **本次只落 §2.1**，其余 **登记进 §8 待办**（同 `ADR-0019` 的处置）。
★ **一句话**：**在协议整洁问题上顺手改，会把问题扩成一次跨里程碑的语义变更。**

**(c) ★★ ⑧ 澄清了两份契约的分工**（这条比它解决的问题更有价值）：

| 契约 | 回答的问题 |
|---|---|
| `data-contract.md` §3.1 `Role` | **落库存哪些字段** |
| `protocol-contract.md` §5.1 角色对象 | **客户端看到哪些字段** |

⇒ **派生而不落库的字段**（`origin` · `maxHp` / `maxMp` …）**只属于后者**。
★ 把派生字段塞进 `Role` 会**造出双真源**（存一份、配置一份，迟早不一致）。

### 4. 顺带补上 `protocol-contract.md` **§9 变更记录**

该文件此前**只有头部一行版本号**，**没有变更台账**（`data-contract.md` 有）。
⇒ v0.4 起补上，并回填 v0.1~v0.3 三行。
★ 理由：**改契约的人需要一处能按版本倒查「改了什么」的地方**，头部那一行写不下两版以上。

### 5. 明确**不改**的两处（避免读者以为漏了）

- **`data-contract.md` 不动** —— 见 §1.3(c)。
- **`ROADMAP.md` 的「契约增量」表不动** —— 本批**不新增实体**（`Account` / `Role` / `RoleRoot` /
  `RealmLevelConfig` / `GameConfig` 五个**早已展开**，`check-contract-gate` 持续为绿）。

**★ 可复用判据（3 条 · 与 ADR-0023 §可复用判据互补）**

1. ★★ **下游上报的「缺口」，上游要按「类型」分别处置** —— 本批 8 处其实是**三类**：
   **安全缺口**（①，最急）· **定义缺失**（③⑥，成本延迟到对接那天才付）· **跨文档不同步**（②⑧，两份契约各写一遍就各错一遍）。
   ⇒ **混在一起批，容易把最急的那条（安全）和最长的那条（定义）用同一种力度处理。**
2. ★★ **契约变更要顺手升级下游的「最优实现」** —— 删掉 `accountId` 后，
   下游的正确行为从「拒绝伪造」变成「根本不读它」。**不写下来，下游会一直停在旧的最优上。**
3. ★ **范围闸门在「契约变更」里同样适用** —— 一条好原则往往牵动多个里程碑；
   **只落当前域 + 登记其余**，否则**一次整洁改动会变成跨里程碑的语义变更**。
